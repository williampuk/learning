Give each layer one job

You should already know FIX Logon, Heartbeat, ResendRequest, the order lifecycle, and basic Java. We’ll use classic tag-value FIX 4.4 over TCP, with a broker acting as the initiator and a simulated venue as the acceptor.

  1. SocketTCP bytes, TLS in production
  2. FramerComplete message and checksum
  3. SessionLogon, sequence, timers, replay
  4. Venue adapterDictionary, IDs, event mapping
  5. Order ledgerIdempotent state and fills

The engine owns FIX sequencing and recovery across TCP connections. The venue adapter translates the counterparty’s rules and messages. The order management system (OMS) owns intent, order state, and reconciliation, and coordinates risk checks before releasing orders. For C42, 34=3 locates a venue-to-broker message in one session sequence cycle. 11=C42, 37=V900, and 17=E2 locate the client order, venue order, and execution in their agreed scopes.

A successful write tells you local transport accepted bytes. A successful Logon tells you the peer established a session. An execution report or other verified venue evidence establishes business state. Keep those signals separate in code, metrics, and incident updates.

If you’re building venue connectivity, keep the engine and implement the venue contract, OMS integration, and certification tests. If you’re building the engine itself, start with a reference peer, build the framer and session owner in stages, and compare behavior under the same fault cases. Both paths use the same C42 trace and have to explain the same final position.

Start with the counterparty contract

Version-control the venue’s rules of engagement, FIX version, custom dictionary, field and group rules, CompIDs, session schedule and time zone, heartbeat, TLS and authentication, traffic limits, and primary/backup behavior. Record when sequence numbers reset, which messages are replayable, whether the venue cancels on disconnect, and how to recover orders or fills through status queries or drop copy, where available.

Read a real venue spec

NYSE Pillar’s equities gateway uses FIX 4.2. Compare §1.3 (failure recovery), §7.5 (retransmission), and §9 (drop copies). Primary/secondary recovery and disaster recovery have different sequence and replay rules. Create separate certification tests for those cases. The lab uses a generic FIX 4.4 profile.     Build the Java engine in stages

    Run the wire lab before implementing your own session behavior. It uses QuickFIX/J 3.0.2 on both ends of a TCP link and gives you a reference trace to compare with your own implementation. From the repository root, run it with JDK 17 or newer, Maven, and a free loopback port 19876.

    mvn -f fix-engine/fix-engine-java/java/pom.xml compile exec:exec

    The harness submits C42 once, forwards the acknowledgement, drops the original E2 frame, and closes both sockets. QuickFIX/J reconnects and requests recovery using separate file stores. The program checks the retransmission headers and prints PASS: replayed E2 applied once. Filled 100, leaves 0. Look for the evidence directory in its output and compare the two *.messages.log files. The console uses | to display the otherwise invisible SOH separators.

    1. Frame bytes, then decode fields

    Keep a buffer per connection. TCP reads can end in the middle of a message or include several messages. Read 8 and 9, then count BodyLength bytes from immediately after the delimiter closing tag 9, up to the start of tag 10. Verify the seven-byte trailer 10=ddd<SOH>. Compute the sum of unsigned bytes before tag 10 modulo 256. Treat lengths as untrusted, cap message size and incomplete-frame time, and retain surplus bytes.

    The Java framer sits inside the lab’s fault link. It uses a buffered blocking stream so the byte boundaries are easy to inspect. A production codec should handle partial writes, stream cumulation, length/data pairs whose values may contain SOH, and dictionary-aware repeating groups. Measure parsing before replacing generic field objects with generated decoders or byte slices. Make buffer ownership explicit when handing data off across threads. FIX tag-value encoding standard

    Build an incremental decoder by feeding one known-good frame at every possible split point, then feeding two frames in one read. Assert that the output bytes match the originals and that an incomplete or malformed frame never reaches the session. Keep outbound frames queued until their last byte has been written.

    2. Model the session and its timers

    Define transitions for disconnected, connecting, awaiting Logon, live, recovering, and logging out. Track next outbound and next expected inbound independently. Give each session one logical owner, such as an event loop that serializes timer ticks, writes, reconnect, and replay. Use a monotonic clock for elapsed time and UTC wall time for FIX timestamps and cross-host evidence.

    Inbound eventEngine responsibility
    Sequence equals expectedValidate and account for the message, then advance according to its type. Keep delivery and checkpoint semantics explicit.
    Sequence above expectedRecord the missing interval, send or extend a resend request under the session policy, and bound pending work. Release higher application messages only in order. Implement special handling of administrative messages according to the profile.
    Sequence below expectedCheck duplicate flags and timestamps. Suppress already-processed retransmissions and handle an unexpected low original according to the standard and venue rules.
    Peer requests resendRead the historical range in sequence order. Re-encode eligible messages using original sequence and sending time in tag 122, current tag 52, 43=Y, and new length/checksum. Gap-fill ranges the profile allows you to skip.
    Peer stops sendingUse the negotiated HeartBtInt and profile rules to drive idle heartbeats, a TestRequest with its identifier, and a disconnect if the peer fails to respond.

    Keep Gap Fill and Reset mode separate. A gap fill advances beyond a skipped interval. A reset can bypass normal recovery and requires a specific operational policy. Include schedule rollover, reconnect backoff, simultaneous recovery in both directions, and duplicate Logon in tests.

    For a custom engine, drive this state machine with decoded messages and a controllable clock before adding sockets. Give it a test store and record the commands it emits, such as send ResendRequest, arm a timer, or deliver an execution. Then connect it to the lab’s reference peer. As a milestone, prove that venue sequence 4 never causes the broker to skip E2 at 3 and that replay leaves the broker’s outbound counter independent.

    3. Decide what survives each crash

    • Outbound. Persist business intent and ID before release. When promising replay after a crash, journal the outbound frame with its assigned sequence before it becomes externally visible. Recover the replay index and next sequence from a consistent committed prefix. Distinguish queued, committed, socket write, peer acknowledged, and business accepted.
    • Inbound. Advance the durable checkpoint once the event is durably applied or recoverable from a durable inbox. Use a transactional inbox or idempotent consumer and test crashes on each side of its commit. Scope execution deduplication to the venue’s ID rules and keep trade corrections and busts as distinct business events.
    • Failover. Fence the old sender before a standby takes the same session identity. Recover journals and counters, reconnect under the venue’s policy, and reconcile in-flight orders before lifting the relevant order-entry gate. A replicated store can still lose uncommitted data.

    A checkpoint is the position that recovery will resume from. Document which failure each acknowledgement and checkpoint can survive. A write into the OS page cache, a forced local append, and a replicated commit have different durability and latency. Test process kill, host loss, disk full, slow flush, partial records, and restore with actual storage settings.

    Store the outbox intent and the assigned sequence so restart can tell an existing submission from a fresh one. If the inbox and session checkpoint live in different stores, a crash after the inbox commit can cause replay. The unique inbox key makes that replay safe. When a journal record never committed, recovery starts from the last committed prefix. A torn record should never look like a successful send.

    For C42, if outbound sequence 2 is committed and the process dies before it records a socket write, recover sequence 2 and its original order identity from the journal. The broker may be unsure how far bytes traveled. Use the venue’s session recovery and order reconciliation rules to choose the next action. Assigning C42 a new sequence as a fresh submission can create a second order.

    4. Integrate QuickFIX/J with the OMS

    Use SessionSettings, a versioned data dictionary, a replay-capable MessageStoreFactory, and an Application implementation. Put peer-specific Logon fields in toAdmin where appropriate. Translate fromApp into small owned events, and keep slow database calls, HTTP calls, and log formatting off shared dispatch threads. Inspect and benchmark the connector’s threading model before choosing shared dispatch or thread-per-session.

    Use a bounded, ordered handoff. An in-memory queue can accept E2, let the session checkpoint advance, and lose E2 on process exit. A durable inbox can make E2 recoverable before the application callback returns, then let a worker apply it later. Budget the inbox commit in callback latency. When storage or capacity fails, hold new order admission and verify how your engine accepts, rejects, or checkpoints the current message. Exercise that exact failure with a real peer or the simulator. QuickFIX/J application API · Session settings · Threading model

    5. Certify failure behavior

    Replay sanitized venue fixtures in CI. Test split and merged reads, wrong body length or checksum, invalid groups, high and unexpectedly low sequences, replay interleaved with new traffic, and reset day boundaries. Kill the process between journal append, send, event commit, and checkpoint. Assert sequence continuity, bounded queues, and one business effect per execution, including after restart. Then run the venue’s certification cases for order, cancel/replace, reject, partial fill, reconnect and recovery, and record the evidence with both sides’ sequence numbers and IDs.

    Run a failover drill with an accepted order whose fill is still uncertain. Check that only one process can send under the session identity, recovery resolves the gap, and the ledger matches the venue before reopening order admission. Model that admission gate separately from TCP and FIX Logon so your application can show why the desk is still waiting.

    Crash between the fill and the checkpoint

    What survives if the broker books E2 at sequence 3 and dies before recording that it expects 4? This JDK-only exercise halts a JVM at that exact point and starts a new process to feed the same fill back to the ledger. Run the lines individually from the repository root in a POSIX shell with JDK 17 or newer.

    cd fix-engine/fix-engine-java/java/src/main/java
lab=learning/fix/CheckpointLab.java
scratch=$(mktemp -d)
java "$lab" crash "$scratch"
java "$lab" replay "$scratch"
java "$lab" replay "$scratch"
    1. crash writes and forces E2.fill, then halts with exit code 73. The record carries the execution identity and 100 filled. The missing next-inbound file means the fixture still expects 3.
    2. The first replay reads the existing fill, recognizes its identity, and writes 4 to next-inbound. Expect E2 already booked. Filled 100. Expected inbound 3 -> 4.
    3. The second replay explicitly feeds E2 to the ledger again. Expect the same quantity and Expected inbound 4 -> 4.

    For a control, replay in a second fresh directory. With no existing E2, expect Booked E2. Filled 100. Expected inbound 3 -> 4. The same delivery works whether the pre-crash commit happened or the process died earlier.

    The fixture treats one keyed file as its whole ledger. A production ledger typically inserts a venue-scoped inbox key and updates order state in the same transaction. The exercise covers a forced process halt after a completed file write. Host loss, partial writes, and replication need their own storage design and tests. CheckpointLab.java · JDK FileChannel.force

    Design for the tail

    The best engine for a workload is the one that meets its latency, peak throughput, recovery, and durability targets together. Start with the representative message mix, session count, sustained rate, burst duration, CPU budget, replay window, and maximum acceptable recovery time. Define the point at which an event counts as durable before measuring it.

    For example, a team might require p99.9 below 2 ms for local handoff at 30,000 messages per second across 20 sessions, and recovery of a 50,000-message gap within 10 seconds while other sessions stay within their limits. These are illustrative acceptance criteria. Publish the offered rate, completed rate, errors, and the exact start and end of each timing interval beside the result.

    Design choiceWhat to measure or protect
    Single writer per session, sessions sharded across loopsOrdered state without contended per-message locks. Check fairness during large replay and isolate busy sessions if necessary.
    Reusable buffers and dictionary-generated codecsBytes allocated per message, GC pauses, and ownership across queues. Represent prices as scale-aware fixed-point values where the venue contract permits.
    Bounded queues and high-water marksQueue age and rejected admissions under bursts. Keep enough capacity for recovery and session traffic while preserving wire ordering.
    Append-only replay journal and range indexMeasure append, commit and replay separately. Group commit trades time waiting for a batch against storage efficiency. Keep replay work bounded so live sessions make progress.
    Selector, dedicated polling, or hybrid idle strategyCompare tail jitter and CPU cost on target hosts. Profile scheduler wakeups, core placement, NUMA locality and NIC interrupts before tuning.
    Separate telemetry from session processingBudget synchronous audit work required by policy. Sample diagnostic counters and make sink lag visible. Exercise full disk, log rotation, and telemetry slowdown.

    Estimate the cost of a burst

    Assume an empty FIFO queue, constant arrivals for 50 ms, one consumer processing 60,000 messages per second, and arrivals stopping after the burst. Predict how much work is still queued when the burst ends.

    40,000 msg/s160,000 msg/s

    2,000 messages waiting

    33.3 ms to drain after arrivals stop

    At 100,000 messages per second, (100,000 − 60,000) × 0.05 = 2,000 messages accumulate. At 60,000 messages per second those take about 33.3 ms to clear, even if the consumer takes only about 16.7 μs per message. If traffic continues, the drain rate is the consumer’s spare capacity. A 1,500-message queue in this example would fill before the burst ends. Define what happens at that boundary before increasing its size.

    Benchmark the promise you make

    1. Use two scopes. Use JMH for a codec or allocation experiment. Use a paced load generator and a separate peer for end-to-end runs with your real dictionaries, TLS, store, validation, logging, and warm-up. Keep hardware, JVM, session mix, and durability constant when comparing engines.
    2. Time meaningful boundaries. Record queue wait, frame decode, application handoff, journal commit, socket write and local order-to-ack round trip. For in-process durations use a monotonic clock. Report p50, p99, p99.9, sample counts, throughput, rejected or timed-out messages, and queue age. A p99 of 2 ms means about 99% of measured samples complete within 2 ms.
    3. Keep offering traffic during pauses. In an open-loop test, schedule arrivals independently of responses and measure from intended arrival. Track late submissions and timeouts. If the generator waits for each reply, it can miss the requests that would have arrived during a stall. This bias is called coordinated omission.
    4. Measure failure under load. Sweep load past saturation, reconnect during a burst, replay a large range while other sessions are live, and inject slow disk or a slow consumer. Report recovery time and correctness alongside latency. Profile before and after each change with allocation data, JFR, CPU and storage metrics.

    Compare QuickFIX/J as a baseline with a low-latency design such as Artio, which separates its gateway and application library and uses Aeron between them. Build a specialized engine when the remaining gap is measured and the team can maintain certification, recovery, and support. If the venue offers a binary protocol, evaluate it as a separate integration with its own contract. Artio architecture · OpenJDK JMH · HdrHistogram and coordinated omission

    Debug a live session from evidence

    Start by identifying the affected session, time range in UTC, last known good event, and orders with uncertain state. Follow the desk’s incident procedure to gate affected order entry and coordinate with trading, risk, and the counterparty. Preserve both directions of the FIX logs, journal positions, the active dictionary and config versions, and deployment or failover events. Keep credentials and customer data out of shared traces.

    Walk the C42 incident

    1. Contain. The broker’s last accepted inbound sequence is 2. Mark C42’s outcome uncertain and keep its original ID. Submitting a new order with a new ID could create a second live order.
    2. Locate the gap. Compare the broker’s expected inbound 3 with the venue’s outbound journal. The reconnect Logon at 4 explains the resend. Check which messages the venue replays or gap-fills.
    3. Prove the fill. Match E2 to V900 and C42. Verify 100 filled and zero leaves in the ledger and any required independent source. If 3 is gap-filled, leave the order unresolved until approved evidence resolves it.
    4. Restore and follow up. Confirm sequence progress, healthy queues, no unexplained fills, and agreement with the desk before resuming the affected flow. Save a redacted timeline, add a regression fixture for the incident, and attach it to the runbook.
    The FIX log shows E2, but the OMS shows zero filled

    Start with the first missing handoff. Suppose the broker’s receive log shows 34=3, 17=E2, 32=100 and the durable session checkpoint says expected inbound 5. Search for E2 in the inbox by its venue-scoped key. If it is absent, check callback errors and inbox admission before the checkpoint moved. If it is present but unapplied, check worker lag and the ledger transaction outcome. If it is marked applied, compare the ledger row and OMS projection versions. A receive log only proves the frame reached the logging point.

    Leave C42 unresolved while you compare venue evidence. Recover E2 through the approved reconciliation path and verify 100 filled, zero leaves and one business effect before closing the incident. The checkpoint alone will not trigger a resend for 3 in this example.

    What to collect during a latency incident

    Capture session event and message logs, peer timestamps and, where permitted, socket and packet evidence. A TLS capture can show timing and connection behavior. Use authorized endpoint logs for FIX fields. Record host clock offset and compare local elapsed times before drawing cross-host latency conclusions.

    What employers mean by FIX experience

    A Java web developer already brings useful skills in validation, idempotency, distributed systems, and incident diagnosis.     Interview exercises

    We sent an order and heard nothing. Can we retry?

    First identify whether the application accepted the command and whether a sequence and durable frame were assigned. Keep the original order identity. Recover the session, then reconcile through replay, approved order status or drop copy before deciding whether another submission is valid under the venue’s rules.

    Our parser got twice as fast. Why did p99.9 barely change?

    Time the full path under the same offered load. Check if storage commits, callback queues, network or scheduler delays dominate the tail. Verify that the load generator kept sending during pauses. An isolated codec win may have little effect on order-to-ack latency.

    How would you turn this lab into a portfolio project?

    For connectivity roles, build a venue profile and show what you do when the peer rejects an order, drops the connection, or recovers with a gap. For engine roles, combine the two labs by adding a transactional inbox to the wire path and injecting the checkpoint crash there. Show that the restarted process recovers E2 once. Include the failure timeline, the commands to reproduce it, and a load comparison with a stated durability boundary.
