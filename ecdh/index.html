Agree on a secret in public

Suppose two programs want to encrypt a conversation, but their network traffic is visible to everyone. Sending a freshly generated AES key would reveal it. ECDH lets each program use a private input and a public message from its peer to calculate the same secret locally. This is key agreement. Encryption is a separate operation that can use a key derived from the result.

Think of a point as a position on a grid that follows a curve equation. The curve also comes with a rule for adding two points to get another point. A private key is a secret integer d, called a scalar. Its public key is a point Q = dG. The public generator G is an agreed starting point, and dG means adding d copies of it using the curve’s addition rule. See the ECDSA guide for a visual introduction to point addition and scalar multiplication.

ECDSA uses that key relationship to sign and verify messages. ECDH uses it to establish shared key material. Each party starts by creating a key pair, then applies the same multiplication operation again using the other party’s public point as the starting point.

Why both sides reach the same point

Imagine Bob has already counted out b copies of G and bundled them into one point B. Alice adds a copies of that bundle, for a groups of b. Bob makes b groups of a using Alice’s point A. Both have counted the same number of copies of G.

Alice’s calculationaB = a(bG) = (ab)G
Bob’s calculationbA = b(aG) = (ba)G

Point addition lets you regroup the copies of G. The equality ab = ba is ordinary integer multiplication. Each person has only one private scalar, and the received point already embodies the other scalar’s contribution.

Work it by hand

Alice chooses a = 7 and publishes A = 7G = (0, 6). Bob chooses b = 5 and publishes B = 5G = (9, 16). With those points in hand, Alice adds seven copies of B and Bob adds five copies of A.

Alice uses Bob’s point7(9, 16) = (10, 11)
Bob uses Alice’s point5(0, 6) = (10, 11)
See the point additions
  1. Alice doubles B to get 2B = (7, 11), then doubles again to get 4B = (5, 1). She adds 4B + 2B = (13, 10), then adds B to get 7B = (10, 11).
  2. Bob doubles A to get 2A = (9, 1), then doubles again to get 4A = (7, 6). He adds A to get 5A = (10, 11).

Where each modulus belongs

Coordinates use mod p
The point-addition formulas work in the field of size p = 17. For example, doubling B = (9, 16) uses slope (3·9² + 2)/(2·16) ≡ 5 (mod 17). Division here means multiplying by the denominator’s inverse in that field. The denominator 32 reduces to 15 and 15·8 ≡ 1 (mod 17), so its inverse is 8. With slope m = 5, the doubled point has coordinates x′ = m² − 2·9 ≡ 7 and y′ = m(9 − x′) − 16 ≡ 11. Each coordinate is reduced mod 17.
Counts of G wrap mod n
Since 19G = 𝒪, every extra 19 copies of G bring you back to the same point. The shared point is 35G = (35 mod 19)G = 16G. This is a check you can make because the example gives you both private scalars.
Try a prediction

Set Alice’s scalar to 1 and keep Bob’s at 5. Where will the shared point land?

Reveal the answer

Alice computes 1B = B and Bob computes 5G = B. The shared point coincides with Bob’s public point at (9, 16). That is one reason a real private scalar must be unpredictable.

What keeps the shared point secret?

A passive observer has G, A, and B. The task of finding (ab)G from those three points is the computational Diffie–Hellman problem. One possible route is to recover a from A = aG, which is the elliptic-curve discrete logarithm problem, and then compute aB. ECDH assumes computing the shared point from public information is infeasible for the chosen group and properly generated keys.

Think of a clock whose stops have arbitrary names. Counting forward with the rule is easy. Seeing a stop’s name gives no simple subtraction operation to recover the count. On our 19-point curve, an observer can still try all 18 private scalars. Real curves have vastly larger groups, and real implementations generate private keys with a cryptographically secure random source. The search-cost walkthrough shows why an attack can be much faster than trying every scalar.

What if someone changes a public point?

A valid point can belong to anyone. If someone can substitute public keys in transit, Alice and Bob can each establish a different secret with that intermediary. In a certificate-authenticated TLS handshake, the server signs the handshake transcript (which includes the exchanged key shares). The client verifies the signature and certificate to bind the exchange to the expected server.

Alice and Bob agreed on a point. Software needs bytes. A curve and protocol specify which coordinate to keep, how many bytes to write, and in which order. Think of it as a file format for the result of a calculation.

Read the shared value in Go

With Go’s standard X25519 implementation, start with your own generated key private and the public bytes you received from a peer. Parse the peer before doing the exchange. The function returns the agreed bytes or an error.

Validation and identity are two different checks

For short Weierstrass ECDH, validate the encoding and check that coordinates are in range and on the specified curve, the point is nonidentity, and subgroup membership holds where required. On the cofactor-one curves P-256 and P-384, all finite on-curve points are in the intended prime-order group. Go’s NewPublicKey handles the NIST-curve point checks. For X25519, the RFC specifies a u-coordinate-only function with its own decoding rules. Go’s NewPublicKey checks the length and ECDH rejects an all-zero shared output, which can occur with a low-order input. Separately authenticate or authorize the peer key under the application’s rules. A well-formed public key can still belong to an adversary. From shared bytes to session keys

The result is input keying material, secret bytes from which a protocol can derive the exact keys it needs. TLS 1.3 feeds the encoded shared value into its HKDF key schedule. Transcript hashes and labels help bind keys to the handshake and separate traffic in each direction.

In ECDHE, the last letter stands for ephemeral. Each peer generates a fresh exchange key pair. After both peers erase the ephemeral private keys and session secrets, compromise of a long-term signing key alone leaves earlier sessions protected. This is forward secrecy. The long-lived storage key later in this guide has a different goal: it must stay usable for old ciphertext. RFC 9846, TLS 1.3 key schedule and ECDH

Count the possibilities, then weigh them

Imagine drawing one of four numbered cards from a bag. Printing each number in two bits tells you how to label the cards. To predict the draw, you also need to know how many copies of each card are in the bag. A key’s byte length is the label width. Its probability distribution tells you which labels an attacker should try first.

Shannon entropy
Average surprise. An outcome of probability q has surprise −log₂(q) bits. The weighted average here is ½·1 + ¼·2 + ⅛·3 + ⅛·3 = 1.75 bits.
Min-entropy
Surprise of the most likely outcome. The first guess wins with probability qmax = ½, so min-entropy is −log₂(½) = 1 bit. A uniform draw has 2 bits by both measures and a 25% first-guess chance.

The support is the set of values with nonzero probability. The support size tells you how many possibilities exist. In the table, try the values from most to least likely. The last column gives the cumulative chance of success after trying that row and all rows above it. Neither entropy measure is a count of operations required by a particular attack. An attacker also needs a way to produce useful guesses and recognize success, such as a valid AES-GCM tag. Always ask what the attacker already knows. NIST SP 800-90B, min-entropy and guessing probability

What a uniform AES key buys you

For a uniform AES-256 key, every 256-bit string is equally likely. With guessing only, trying m distinct keys covers exactly m / 2²⁵⁶ of the distribution. Bias can put more probability on the first few guesses. A known fixed bit, for example, halves the candidate space without making it small. A small mathematical bias may have little practical effect, especially when finding or testing the favored keys is hard.

Statistical uniformity
All strings have exactly equal probability. Statistical closeness measures the size of the deviation, even for an observer with unlimited computation.
Computational pseudorandomness
Within the security model, a feasible observer cannot reliably tell the output from random. The set of outputs can still be smaller than the entire space.
Unpredictability and attack cost
Guessing the exact key is different from distinguishing its distribution. Recovering a key, distinguishing outputs, and breaking an enclosing protocol can each have different costs.

Kerckhoffs’s principle tells us to assume the attacker knows the algorithms and public metadata. Uniform keys give the attacker no preferred candidates in the ideal key-guessing model. A good KDF aims to give applications pseudorandom keys under stated assumptions, without depending on hiding the derivation.

Four secrets in a 256-key space

Give a toy system only four equiprobable source values 00 through 03 in hexadecimal. An eight-bit key can represent 256 values. Compare zero-padding the source with a public lookup that scatters the same four inputs across the space.

The general rule. Fix all public inputs and call the deterministic derivation K = f(Z), where Z is the secret byte string and K is the key. Every possible Z leads to one K. Multiple inputs can also lead to the same key. The reachable-key set can only stay the same size or shrink. For someone who knows the four reachable bytes, membership in that set distinguishes this toy output from a uniform byte. A uniform byte lands there only 4 times out of 256 on average. Output probabilities for colliding inputs add together, so the best first guess can only stay as good or get better. Shannon entropy cannot rise either: learning the output cannot tell you more about the outcome than learning the entire input.

If a hypothetical source has exactly 2¹²⁸ possible values, and they are efficiently enumerable, the attacker can derive each candidate key and test it. Even with 256-bit outputs there are at most 2¹²⁸ candidates. HKDF adds a small cost per candidate. It supplies neither new secret randomness nor a password-stretching work factor. Hashing a guessable password with HKDF still lets the attacker test likely guesses cheaply. Where a password is the source, a password KDF such as Argon2id increases the cost of each guess. If a fresh salt is public, the same reasoning applies after the attacker sees that salt. RFC 9106, Argon2

P-256 attack cost is a different number

The P-256 group has about 2²⁵⁶ points. For a fixed valid nonidentity peer point, multiplying by a uniformly chosen nonzero scalar runs through all nonidentity points. Encoding only x pairs each point with its negative, so the coordinate support is roughly 2²⁵⁵. This counts possible values across generated keys. It makes no claim about what an observer can efficiently calculate for one recorded exchange.

First expression2A + G = 15G
Second expressionA + 8G = 15G

Here A = aG from the lab. If a search finds those two expressions land on the same point, their coefficients give 2a + 1 ≡ a + 8 (mod 19), so a = 7. The search can compare points without knowing a. Pollard rho uses a pseudorandom walk with tracked coefficients to find a collision, like looking for a shared birthday among many pairs of people. In a group of order n, a useful collision takes on the order of √n group operations in the generic model. Recovering a private scalar this way and multiplying by the other public point breaks that exchange.

The roughly 2¹²⁸ classical work factor for P-256 comes from this square-root scale. X25519 is also commonly described as targeting about 128-bit classical security, with a different group and parameters. The overall system can be weaker if a key is guessable, an endpoint leaks it, or the protocol exposes a cheaper attack. Deriving a 32-byte AES key does not change the curve’s work factor. For fixed public shares the correct result is already determined mathematically. Its secrecy is computational. NIST SP 800-57 Part 1 Rev. 5, Table 2 · RFC 7748 §4.1 · Pollard’s collision method

A 32-byte key is derived from four equiprobable secrets using a fixed public KDF. How many keys are reachable? What is the attacker’s best chance on the first guess?

At most four keys are reachable. The best guess succeeds with at least 25% probability if the attacker knows the source distribution and can compute the outputs. A collision can make that probability higher.

Turn shared material into purpose-specific keys

Imagine a recipe that makes one base mixture, then uses separate instructions to make each finished product. A KDF gives software a similar interface. It takes the shared material and produces the number of bytes each consumer expects under a distinct label.

HMAC uses a hash function and a key to compute a digest of a message. A hash takes any-length input and returns a fixed-size digest. HMAC defines how to incorporate a key and behaves like a keyed pseudorandom function under standard assumptions when the key is suitable. During Extract the salt occupies HMAC’s key input even though it can be public. During Expand the secret PRK occupies the key input. RFC 2104, HMAC · RFC 5869 §2

The two operations

PRK = HMAC(salt, Z)
T(0) = empty
T(i) = HMAC(PRK, T(i − 1) || info || byte(i))
OKM = first L bytes of T(1) || T(2) || …

i is a counter starting at 1, encoded as one byte. Each block T(i) includes the previous block and the same info label. With SHA-256, each block is 32 bytes, so a 32-byte AES key takes one block. The limit is 255 blocks, or 8160 bytes with SHA-256. Output length truncates the same stream, so the 16-byte result is a prefix of the 32-byte result for identical inputs and label. Use distinct labels if the outputs are meant for different purposes.

Toy trace. Suppose a pretend two-byte HMAC returns 2a 91 in Extract. With label enc, let the first block be b0 74 and the second be 35 9c. A request for three bytes takes b0 74 35. Can raw ECDH bytes be an AES key?

From AES’s point of view, every 32-byte string is a valid AES-256 key. Direct use can be defensible in a narrowly reviewed design with a fixed curve and API, validated output, adequate secret quality, a single well-defined use, and no protocol requirement for a KDF. That design accepts dependence on the raw coordinate representation and its distribution. Omitting HKDF does not by itself make properly generated X25519 output cheaply guessable.

PipelineWhat it providesIf the source is guessable

Z → HKDF → AESStandardized extraction for input such as DH output, selectable length, and purpose separation. Under suitable source and HMAC assumptions, keys for distinct contexts can be treated as pseudorandom.Run HKDF for each candidate, then test it.

HKDF’s concrete benefits are a well-studied key schedule and the ability to prevent accidental key reuse across contexts. In a single-purpose system with a strong, fixed source, some of these benefits may be small. HKDF still cannot authenticate a peer, repair a publicly computable Z, or lift the attack cost above a cheaper break of the ECDH exchange. Use the chosen protocol’s KDF and validation rules, including any compliance requirements. RFC 5869 §3.3, Extract and DH inputs · NIST SP 800-56C Rev. 2

Move the private key into a smart card

Think of the card as a calculator that takes a public point and uses a stored private scalar. The host can request a calculation without reading the scalar. It still receives the result, and in this design it uses that result for key derivation and encryption.

What the pinned Go library actually does

  1. Get the decipher-key handle. Open the OpenPGP applet, select an already provisioned decipher key, and match its public key to a trusted copy. *openpgp.PrivateKeyECDH is a handle for the operation.
  2. Prepare the peer key. Use the curve’s NewPublicKey parser. PrivateKeyECDH.ECDH also checks that the peer curve matches the configured curve.
  3. Send the command. Version v0.3.11 nests peer.Bytes() in the external public-key object 86, public-key object 7F49, and cipher object A6. It sends PSO: DECIPHER with instruction 2A and parameters 80 86. This request is an APDU, the message unit used between a host and a card. The normal default is the decipher slot; the optional Manage Security Environment command can switch the active key on supporting cards.
  4. Read the shared bytes. The library passes through the response data on success. It applies no KDF, point conversion, output-length check, or all-zero check. OpenPGP Card 3.4.1 §7.2.11 describes the uncompressed 04 || x || y input for conventional curves and returns the shared secret. The pinned package tests compare card output byte-for-byte with Go ECDH on P-256, P-384, P-521, and X25519 using YubiKey 5.4.3 fixtures. For those profiles this means fixed-width big-endian x for the NIST curves and raw 32-byte little-endian u for X25519. The X25519 fixture also sends a bare 32-byte peer key. The conventional point-format paragraph alone does not specify this X25519 behavior for every card.

What the hardware boundary protects

On-card key generation can keep the long-term scalar out of host backups, process memory, and logs. A key imported from software already existed outside that boundary. The ECDH response, derived AES key, and decrypted plaintext all enter host memory in this example. Malware on a host can copy those values or make requests to an unlocked card. Card PIN and touch requirements control use according to model and configuration. They do not give the card an understanding of which object the caller is authorized to decrypt.

A card that evaluates ECDH on inputs chosen by a caller is an oracle for those evaluations. Restrict access and authorize requests before giving untrusted callers control of them. For Weierstrass curves, validate peers in the host and use firmware that validates inputs at the card boundary as well. The fixed card scalar must not be applied to arbitrary invalid points. For X25519, enforce the defined input format and reject an all-zero output even if the card returns success. Validate the expected width for every profile. Validate on actual hardware and firmware before relying on the wire format and operation policy.

The smart-card Go example accepts an existing reader connection and a pinned card public key. It selects the applet, verifies the decipher PIN, calls ECDH, checks the result, and derives a purpose-specific key. Compile it alongside storage-demo.go in a separate Go module after adding cunicu.li/go-openpgp-card@v0.3.11 with go get. The selected device must expose its decipher public key so the example can check it against the trusted copy. The card flow was checked against the source and recorded fixtures, without a live reader. This page’s software demo runs independently.

The card command is a primitive. Historical OpenPGP ECDH uses the RFC 6637-style KDF and AES key wrap outside the card. RFC 9580 retains that construction for the classic ECDH algorithm and specifies a different schedule for its native X25519 packet algorithm. A custom nil-salt storage example does not produce an OpenPGP message. RFC 6637 §8 · RFC 9580 §11.5

Reproduce an object’s key without storing a salt

Reproducibility means restoring a saved ciphertext with the same derivation inputs. It helps to think of those inputs as part of the file format. The card key, peer value, curve, encoding, and derivation parameters must all agree with the version used to write the object.

Object separation answers “Which object is this key for?” Purpose separation answers “What may use it?” If each object already has its own independently generated peer input, repeating the object ID in HKDF is less important for producing distinct keys, but binding the expected ID in authenticated data can prevent swapping objects between records. A fixed, versioned HKDF label is still useful. Encryption and a separate message-authentication function should derive different keys, even for the same object. AES-GCM already authenticates its ciphertext and AAD, so it needs no additional MAC for that job.

A public peer scalar defeats the hardware boundary

Suppose the peer scalar dobject comes from a public hash of the plaintext or an object ID, mapped into the valid scalar range. The hardware scalar is dhardware. Their public points are P_object = d_object · G and P_hardware = d_hardware · G.

Card knows its own scalard_hardware · P_object
= (d_hardware · d_object)G
Observer knows or guesses the object scalard_object · P_hardware
= (d_object · d_hardware)G

The integer products are equal, so both calculations yield the same point and the same encoded bytes. On the toy curve, use hardware scalar 7 with public point (0, 6). Let a public mapping give the object scalar 5, with object point (9, 16). The card computes 7(9, 16) = (10, 11). Anyone who knows 5 computes 5(0, 6) = (10, 11). Try it using the exchange sliders.

Imagine storing a signed standard-form letter with just two plausible versions. Someone who knows the template can compute the public mapping for both candidate documents. A stored peer public key can confirm a guess directly, and an authentication tag can confirm the matching derived key. Once someone knows or guesses the scalar, the public hardware key gives them the shared bytes without the card. HKDF sees the same inputs on both paths, so it yields the same AES key.

How will decryption get the peer value?

If decryption needs the plaintext to reconstruct the peer key, the process is circular. Store the peer public key with the ciphertext, or derive it from a stable identifier already available to the decryptor. Publishing an ID or point is compatible with many key-agreement designs. Publishing enough information for anyone to reconstruct a peer private scalar is what causes the failure above. A public hash of a small plaintext dictionary also leaks information even if the hash is labeled an identifier.

Three designs and what each depends on

Random ephemeral peer; store its public key
To encrypt, generate a fresh random peer scalar, compute ECDH with the trusted recipient public key, and keep only the public share with the ciphertext. The recipient card can reproduce the shared secret years later from the public share. This requires per-object public metadata but no saved HKDF salt. The encryptor knows the secret during encryption. Anyone with the recipient’s public key can create their own new encrypted objects, so authenticate the writer separately if needed. For production public-key encryption, a reviewed format such as HPKE specifies peer/transcript binding and authenticated variants. Use a card integration that supports the selected suite. RFC 9180, HPKE
Stable secret plus a public object ID
If a protected secret source is already available, expand purpose- and object-specific keys under that secret using a versioned, unambiguous context. A card can recompute a base secret from a fixed, independently generated peer point whose scalar was kept private during setup and then destroyed. A holder of the base secret can derive every object key in that domain. If the hardware instead offers a reviewed keyed derivation service, use its specified interface. A public ID is safe as a label and supplies no secrecy.
Standardized hash-to-curve; evaluate a point with unknown discrete log
RFC 9380 specifies how to map bytes to a curve point, using field mappings and suite-specific subgroup handling. A recipient of that point can recompute it from a known message but, on the real curve under the intended assumptions, has no efficient way to recover a scalar relating it to G. This removes the known-scalar shortcut. An RFC 9380 suite specifies the mapping, while authorization, ECDH encoding, output derivation, and the storage security model still need design and review. Verify that the card accepts the selected curve, point form, subgroup, and output representation. In particular a suite producing an Edwards point is not a drop-in X25519 input. A card oracle that evaluates the target point for an attacker still defeats the design. RFC 9380 §8, suites · RFC 9497, a reviewed protocol using hash-to-curve

Which design lets an encryptor use only the recipient’s public key while keeping a guessable plaintext confidential? What should it save?

A fresh random ephemeral peer, under a suitable public-key encryption protocol. Save the ephemeral public share, version and recipient key identifier, and whatever the encryption format needs to recover the nonce and authenticate the metadata. Encrypt the object with AES-GCM

The AES key is a secret that can stay the same while a file is updated. Think of the nonce as a public serial number for one encryption under that key. GCM uses it to start encryption in a different state. The serial number travels with the encrypted object.

Key
AES accepts 16, 24, or 32 bytes. This example requires 32 bytes explicitly. These correspond to AES-128, AES-192, and AES-256.
Nonce or IV
GCM uses an initialization vector as a nonce. A common size is 12 bytes. A nonce must be unique for every encryption under the same key, with carefully bounded collision risk if generated randomly.
Ciphertext and authentication tag
Encryption hides the plaintext. The tag lets decryption reject changes to the ciphertext or authenticated metadata. Check it before consuming any plaintext.
Additional authenticated data (AAD)
Bytes kept in the clear but bound by the tag. Authenticate the version, key identifier, and peer share. Bind the expected object ID from the caller’s trusted record when you need to prevent cross-object swapping.

Encrypt by generating a fresh peer key for a new record, deriving the AES key, then sealing with a fresh random nonce. Decrypt by parsing the header, choosing the pinned recipient key, validating the peer, reproducing the AES key, and authenticating the record with the expected AAD. A different version, ID, key, or tag should yield an error. In a card-backed deployment only the recipient-side multiplication moves onto the card.

Reusing a nonce under the same GCM key reuses the encryption keystream. Comparing the two ciphertexts exposes the XOR of the two plaintexts, and the reuse can also enable tag forgery. Different keys have separate nonce spaces. A rewrite, retry, or restored snapshot can reuse an object’s key, so relying on “one encryption per object” is brittle. Go’s NewGCMWithRandomNonce generates and prepends a 96-bit nonce and extracts it during Open. Its contract limits usage to at most 2³² encryptions per key. NIST SP 800-38D §§8 and A · Go GCM nonce API

Other modes fit different problems. CTR provides confidentiality with a unique counter stream and needs separate authentication. CBC needs a suitable IV and separate authentication. AES-SIV can encrypt deterministically and preserve integrity, with equality leakage for repeated plaintext and AAD under one key. AES-GCM-SIV still takes a nonce and is designed to limit damage from accidental repeats. With a repeated nonce it can reveal equality for identical inputs. Prefer fresh nonces even there unless a reviewed deterministic scheme is an explicit requirement. Disk encryption commonly uses XTS, which has a different job. Unlock a LUKS volume with derived bytes

Imagine a safe with several locks. Each lock opens access to the same contents. A LUKS keyslot is like one lock. A passphrase or binary key file provides the credential for that slot. The volume key is what the disk-encryption layer uses on every sector.

A binary key file is read as credential bytes. Preserve them exactly, with no hex encoding or trailing newline unless that is how the keyslot was set up. A LUKS2 slot commonly uses Argon2 or PBKDF2 according to its configuration. Its salt and cost parameters are managed in the LUKS metadata. Using nil salt in the application’s HKDF leaves these slot parameters intact. cryptsetup FAQ, key files and keyslots · LUKS2 on-disk format

AES-XTS in numbers. XTS uses two AES keys. One encrypts the data blocks, and the other helps generate the tweak for the data-unit number. A sector number is like a position label, so blocks at different locations are processed differently. AES-256-XTS means two 256-bit keys, hence --key-size 512 and 64 raw bytes. It does not mean 512-bit security. XTS provides storage confidentiality without a GCM-style authentication tag. Sector location and mapping parameters matter during recovery. See the cryptsetup arguments for each approach

These are alternative examples for new disposable image files. Formatting writes a new header and can destroy access to existing data. For an existing volume, enroll a new slot using luksAddKey and an existing authorized credential. The Go example derives the two kinds of bytes in memory. These commands assume the respective secure binary file already exists.

# A: the bytes go into the first keyslot as a credential
cryptsetup luksFormat --type luks2 --key-file slot.bin ./new-slot.img
cryptsetup open --type luks --test-passphrase --key-file slot.bin ./new-slot.img

# B: choose the actual 64-byte volume key and protect a slot with a prompted credential
cryptsetup luksFormat --type luks2 --cipher aes-xts-plain64 --key-size 512 \
  --volume-key-file volume.bin ./new-volume.img
cryptsetup open --type luks --test-passphrase --volume-key-file volume.bin ./new-volume.img

Treat both binary files as secrets. In particular, possession of the raw volume key bypasses keyslot protection. luksFormat · open · cryptsetup options

In most cases the goal is to unlock the existing volume without retaining a separate derivation salt. Approach A meets that goal while preserving normal LUKS recovery slots. A fresh format normally creates a different random volume key even if the credential is unchanged. Approach B can reproduce the old raw key, but recreating a compatible mapping requires the original geometry and cipher settings, and overwritten headers or data sectors cannot be reconstructed from a key. Back up the header with luksHeaderBackup and keep a separate data backup. A header backup plus a credential valid at backup time can retain access after slot changes, so protect old copies. A lost or damaged card with no recovery slot, backup key, or other access path can make the volume unrecoverable. luksHeaderBackup · cryptsetup recovery FAQ

Check your understanding

You know the deterministic keyslot credential from A. The device was reformatted with that same credential. Can you recover the old sectors using the new header?

The new slot unlocks the new random volume key. Old ciphertext needs the original volume key and matching parameters. A matching header backup and the relevant credential can recover that key, provided the original encrypted data is intact.

Evaluate a design from the attacker’s side

Start with an observer who knows all the algorithms and public metadata. Then ask what changes if they can submit inputs, control the host, or break recovery. The cheapest available route determines the practical security.

ScenarioTypeConsequence and response
Known or guessable objectPractical attack on public-scalar designsThe observer can derive or guess the peer scalar and reproduce the key from the public card key. A random ephemeral scalar or suitable protected secret source removes that path.
Known algorithms, card public key, peer key, and encrypted recordExpected exposurePublic values are part of the security model. For honest random peers, the observer still faces the ECDH assumption. Length and unencrypted metadata can leak information. Authenticate the metadata and limit what the format exposes.
Caller chooses a peer, or substitutes one in transitPractical if access or authentication is missingA chosen public key can have a scalar the caller knows. Bind the intended recipient, authorize the peer or object, and authenticate the exchange where required. Recipient public-key encryption alone does not prove who wrote an object.

Common misconceptions

Predict each answer before opening it. The examples above give you the reasoning for each case.

Does a 32-byte ECDH result give 256-bit security?

Its size is the encoded field width. Roughly 128-bit classical security for curves such as P-256 comes from known attack costs. System security can be weaker than either the curve or AES.

Can HKDF turn 128 bits of entropy into 256 bits?

For fixed public inputs, a deterministic function maps each secret to one output. An output can be 256 bits wide while the underlying uncertainty stays the same or decreases.

Must an attacker guess all 256-bit AES keys after HKDF?

If the attacker can efficiently enumerate plausible sources, they can derive and test those keys instead. An attack that recovers a private scalar can bypass key guessing entirely.

Does HKDF work because the derivation is hidden?

The algorithm, format, and context labels can all be public. Security rests on secret input and the properties of the cryptographic functions and protocol.

Does any bias make key guessing practical?

Guessing depends on the probability mass an attacker can reach and test with their budget. A known fixed bit changes the ideal guess space by a factor of two. A secret chosen from four known values changes it far more.

Does P-256 have only 2¹²⁸ shared secrets?

The group has about 2²⁵⁶ points. The coordinate has roughly half as many possible encodings. Generic discrete-log attacks work on a square-root scale, which is where the 128-bit estimate comes from.

Does rebuilding the same AES key require identical ciphertext?

A fresh GCM nonce yields a different encryption under the same key. In the software demo a new peer scalar and each encryption nonce draw randomness. Re-derivation from old public bytes and a fixed salt rule does not.

Does a public object-derived point force an attacker to use the card?

If the attacker can recover the scalar behind that point, they multiply the card’s public key by it. A standardized hash-to-curve point instead aims to hide that scalar even when the message and point are public.

Is a LUKS key file the disk-encryption key?

A normal key file unlocks a slot. That slot gives access to the volume key. Only an explicitly supplied raw volume key, such as with --volume-key-file, goes directly into the volume-key role.

Where does a hash-to-curve scheme still need access control?

Anyone can map the object ID to a point. Someone who can send that target point to the unlocked card and read its result can reproduce the same key. The mapping alone cannot enforce who may decrypt.
