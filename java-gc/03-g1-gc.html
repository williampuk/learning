G1 Garbage Collection

Product lookups are usually fast. Then a few customers export the catalog, and even simple requests start running late. What changed in your Spring Boot e-commerce API with an 8 GiB heap?

You are almost certainly already running G1 in production. It has been HotSpot’s server-class default since Java 9, including JDK 21 and 25. G1 took over from Parallel GC to give typical server workloads shorter, more predictable collection pauses while maintaining good throughput. Small JVMs and explicit collector flags can change that selection.

The heap holds Java objects. An object is unreachable when running code can no longer reach it through a reference, so the JVM can reclaim its space. Try the lab to see how that affects requests.

The Smart Restaurant Floor Manager

A busy manager divides the floor into 32 equal square zones. When there’s a short break in service, say 200 ms in our toy restaurant, staff start with zones piled high with empty plates. They move any meals still being eaten to clear tables and reopen the zones they’ve emptied. Picking a zone with one meal and seven empty plates means moving one meal to free an entire zone. That’s the idea behind the name Garbage-First (G1).

Floor zones → heap regions
A region is an equally sized piece of the heap. Free regions can take on a new role as the application allocates.
Empty plates → unreachable objects
Marking traces which objects are still reachable. Much of it runs concurrently, while Tomcat can still serve requests.
Move the meals → evacuate live objects
During evacuation, Java threads pause while GC workers copy live objects out and release the selected regions. A normal young pause covers Eden and Survivor. A mixed pause also takes selected Old regions.
Short break → pause-time goal
G1 estimates how much work it can do in the pause, then gives preference to Old regions that offer more space back for the effort. Copying live objects and scanning incoming references both take time.

Choose what fits in the pause

Most new objects start in Eden. When the JVM finds they’re still in use, it may move them to Survivor and eventually to Old. Look for Old tiles with the most hollow dots. They have more garbage to collect and fewer live objects to copy.

Worked example and Full GC walkthrough
  1. Make a mixed collection plan. Young work costs 36 ms in the starting heap. The marked Old candidates, from most to least garbage, cost 30, 36, 44, 52, 60, and 70 ms. At 200 ms, G1’s toy planner picks R03, R09, R14, and R22 for 198 ms of predicted work. All eight young regions go too. At 50 ms, the first Old region is still required for progress, so the plan takes 66 ms. At 500 ms all six fit for 328 ms.
  2. Evacuate those regions. At 200 ms, six live Eden objects move to one Survivor region. Four live Survivor objects promote to Old and join ten live objects copied from the selected Old regions. Together they use two new Old regions. Twelve source regions become free, three destination regions are used, and 60 unreachable toy objects are recycled.
  3. Try a fragmented heap. Simulate Traffic Spike loads a scenario with 24 free regions, all isolated by Old regions. Click the 8 MB export allocation. Its 8 MiB byte[] payload plus header needs three consecutive 4 MiB regions. Here ordinary collection has made no such run available. Step through the Full GC: the application stops, Old objects compact into 15 regions in the toy model, and the allocation succeeds on retry.

The grid shows 48 regions, whereas the restaurant uses 32. The 4 MiB region size matches a JDK 25 run with an 8 GiB maximum heap. The lab’s 192 MiB map, eight toy object slots per ordinary region, cost model, and fixed heap capacity are for teaching. Heap used counts all non-free region capacity, including unused space in the last region of a humongous allocation. The dots on Humongous tiles show portions of one reserved span. The lab depicts the concurrent part of marking. HotSpot also has stop-the-world phases such as Remark. Real G1 scores Old candidates by reclaimable space and collection cost, adapts the young generation, and can choose additional Old regions during the pause. It can try other collections or expand the heap before Full GC. Finishing exports drops the lab’s last references to its primitive arrays. The next young or mixed pause models G1’s eager reclamation of eligible arrays; in HotSpot that depends on the references G1 observes.

Read a JDK 25 G1 log

Run a Spring Boot jar with unified GC logging. MaxGCPauseMillis is a soft goal. A pause can exceed 200 ms, and the flag does not set an HTTP request deadline.

java -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -Xlog:gc* -jar api.jar

The lines below are from an OpenJDK Temurin 25.0.4 test run with a 128 MiB heap. Open a line for its breakdown, then hover, focus, or select an individual field.

[0.003s][info][gc ] Using G1

The startup banner confirms which collector this JVM selected. The bracketed parts show JVM uptime, log level, and log tags.

[0.359s][info][gc ] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 38M->12M(128M) 2.979ms

GC event 0 ended at 0.359 s of uptime. G1 evacuated young regions and paused Java threads for 2.979 ms. Used heap fell from about 38 to 12 MiB out of 128 MiB currently committed.

[0.453s][info][gc ] GC(19) Pause Young (Mixed) (G1 Evacuation Pause) 119M->50M(128M) 0.411ms

“Mixed” means G1 also evacuated selected Old regions. A concurrent mark cycle finished at 0.448 s. The mixed collection freed about 69 MiB overall, with a net decrease of one Old region. That net count does not tell you how many Old regions G1 selected because copies and promotions can use new Old regions.

[0.453s][info][gc,heap ] GC(19) Old regions: 33->32
[0.453s][info][gc,heap ] GC(19) Humongous regions: 18->18

These are region counts for the same event. Old dropped from 33 to 32. The separate Humongous count stayed at 18. The test heap used 1 MiB regions, so two retained 8 MiB payload arrays plus headers occupied nine regions each.

Reproduce the log with JDK 25

Save this as G1LogDemo.java. Short-lived 32 KiB buffers represent normal lookups, the cache keeps some buffers alive, and two exports overlap. Times, counts, and the exact sequence vary by run.

import java.util.ArrayDeque;

class G1LogDemo {
    static volatile byte[] request;
    static final byte[][] cache = new byte[800][];
    static final ArrayDeque<byte[]> inFlight = new ArrayDeque<>();

    public static void main(String[] args) {
        for (int phase = 0; phase < 5; phase++) {
            for (int i = 0; i < 22_000; i++) {
                request = new byte[32 * 1024];
                if (i < cache.length && (phase == 0 || i % 10 == 0)) {
                    cache[i] = request;
                }
                if (i % 4_000 == 0) {
                    inFlight.addLast(new byte[8 * 1024 * 1024]);
                    if (inFlight.size() > 2) inFlight.removeFirst();
                }
            }
        }
    }
}
java -Xms128m -Xmx128m -XX:ActiveProcessorCount=4 -XX:+UseG1GC -XX:MaxGCPauseMillis=200 '-Xlog:gc*:file=g1-demo.log' G1LogDemo.java

What to tune on a web service

  1. Confirm G1 and correlate the pauses. Look for Using G1 and the startup Heap Region Size. Line up pause duration and frequency with p99 latency, the time below which 99% of requests finished. Check request queues and CPU throttling in the same window.
  2. Look for large allocations and retention. A single object over half a G1 region is humongous and goes straight into a contiguous run in the old generation. Check Humongous regions for sustained growth and use allocation profiling to find large byte[] or String backing arrays. Large buffers stay live while requests, queues, or caches hold references.
  3. Change the export path first. Write JSON in bounded batches to the response, page the database reads, and limit simultaneous exports. Check that downstream layers also avoid buffering the entire response. Assembling a large String before encoding can create another large buffer.
  4. Keep the flag set small. Start with G1’s adaptive defaults and size -Xmx with room for metaspace, thread stacks, direct buffers, and other memory outside the heap. Try a different pause target only after measuring. Fixing young size with -Xmn or -XX:NewRatio takes away one of G1’s main controls.
  5. Investigate Full GC before changing collectors. A request can fail to find a contiguous run or an evacuation can run short of space for live copies. Repeated Pause Full (G1 Compaction Pause) calls for checking allocation rate, live-set growth, and headroom. If healthy G1 still causes your service to miss its tail-latency objective, compare Generational ZGC (-XX:+UseZGC) on the same load. Test latency, CPU, throughput, and memory headroom together.

All rows and their serialized bytes can be live together. Each overlapping export can add another large array.

After · Streaming & paged

// Spring MVC + Jackson 2
@GetMapping("/products/export")
ResponseEntity<StreamingResponseBody> exportProducts() {
    ObjectWriter rows = objectMapper.writer()
        .without(SerializationFeature.FLUSH_AFTER_WRITE_VALUE);
    StreamingResponseBody body = out -> {
        Pageable page = PageRequest.of(0, 200, Sort.by("id"));
        try (JsonGenerator json =
                 objectMapper.getFactory().createGenerator(out)) {
            json.disable(JsonGenerator.Feature.AUTO_CLOSE_TARGET);
            json.writeStartArray();
            while (true) {
                Slice<Product> batch = repository.findAllBy(page);
                for (Product product : batch) {
                    rows.writeValue(json, new ExportProduct(
                        product.getId(), product.getName()));
                }
                json.flush();
                if (!batch.hasNext()) break;
                page = batch.nextPageable();
            }
            json.writeEndArray();
        }
    };
    return ResponseEntity.ok()
        .contentType(MediaType.APPLICATION_JSON)
        .body(body);
}

Jackson writes one JSON array directly to the response stream, flushing once per slice. Rows and temporary objects can become unreachable a slice at a time, often while still in Eden.

Declare Slice<Product> findAllBy(Pageable page) on your Spring Data repository. ExportProduct is the same ID-and-name record used on both paths. Read the scalar fields needed by that record and keep the persistence context scoped to each slice so it can release the entities. A Slice tells you whether another batch exists without requiring a total row count. Check that servlet and proxy layers send the response incrementally.

Check your intuition

At 50 ms, why does the toy mixed pause plan 66 ms?

Show explanation

Young work costs 36 ms, and the first Old candidate adds 30 ms for progress. The target can be exceeded.

Why can an 8 MiB payload fail to fit in 24 free regions?

Show explanation

With 4 MiB regions, an 8 MiB payload plus its array header spans three regions. They must be adjacent in heap address order.

Exports drive up Humongous regions and p99. What should you try first?
