Java Garbage Collection

GET /orders starts missing its latency target during a burst. The SQL is still fast. Where do all the objects from those requests go? Follow one response from database rows to JSON, then see how traffic fills memory and how Java recovers space.

You’ll use familiar Spring Boot, JPA, Streams, and Jackson code. Start here even if you’ve never read a GC log.

One request, many allocations

This controller turns the 50 newest JPA orders into DTOs (data transfer objects). It returns a list, which Spring MVC hands to Jackson to write as JSON. Follow the highlighted expressions and the work that happens after return.

  1. 09 · Query results Hibernate can materialize Order entities, their field values, a result list and its storage, plus bookkeeping for managed entities. Already-managed entities can be reused.
  2. 10 · Response list The ArrayList holds references to the DTOs. A nonempty result gets a backing Object[], sized here from the row count.
  3. 11–12 · Traversal and mapping The stream needs traversal state (typically a Spliterator for an ArrayList, sometimes backed by an iterator for other lists), pipeline stages, and callbacks. Those helpers serve the whole traversal.
  4. 16–17 · Per-row strings and DTOs For 50 rows, the code builds 50 DTOs and 50 formatted labels, with storage for the label contents. The ID is a primitive in the DTO. The existing BigDecimal is passed by reference.
  5. After 13 · JSON output Jackson uses a JSON generator, output buffers, and traversal helpers. It can borrow and recycle buffers as it streams bytes to the server response. This route can write JSON without building one big JSON String.

Multiply the work by the traffic. At 1,000 requests per second, 50 rows per response means 50,000 DTOs and 50,000 labels per second at the source-code level. If you measured 200 kB of total Java heap allocations per request, that would be about 200 MB/s. Actual allocation depends on rows returned, framework behavior, buffer reuse, and what the JVM optimizes away.

Why GC exists. The heap, where Java stores objects and arrays, has finite space. Once the response is written and its request and persistence context release their references, many of these objects can no longer be reached. Garbage collection (GC) makes their memory available to the next request. A shared cache that keeps a reference changes that lifetime.

The busy coffee shop

Paper cups pile up during the morning rush. The counter bin is small, so staff empty it frequently. Trays for orders still being served get moved aside and checked again. The espresso machine stays on the counter all day.

Cup bin → Eden
Eden holds recent allocations in this classic young-generation model. Most cups stand for temporary DTOs, strings, lists, and working buffers.
Tray stations → Survivor S0 / S1
A running order can still reach its tray. In a classic copying layout, each young collection copies objects it keeps into the other survivor space or promotes them. S0 and S1 alternate roles.
Espresso machine → Old Gen
A Spring singleton @Service or shared cache may stay reachable for the life of the app. It can end up in old generation after surviving collections, just as a long-lived tray can move to the shelf.

The generational hypothesis is that most objects die young. Grouping newer objects together lets a collector recover lots of space without walking all the old objects on every pass. A young collection still has to account for references from old objects, such as a cache holding a new DTO.

Work through the first burst by hand
  1. Five requests add 60 blocks to Eden. Each request creates 12 equal 0.1 MB teaching blocks (1.2 MB), so that one simulated second of allocation is 6.0 MB/s. Eleven blocks per request are already unreachable at this snapshot. The response writer still holds one payload per request.
  2. Eden fills, so a Minor GC starts. It reclaims 55 of 60 Eden blocks (91.7%) and copies the five reachable payloads into S0. Resuming lets the next group of requests start. The simulated pause includes a small cost for each block kept.
  3. Before the next group starts, the previous responses finish. With the cache off, their five payloads become unreachable and are reclaimed on the next young collection. The next five live payloads land in S1.
  4. With the cache on from the start, the first five payloads stay reachable across both collections and promote into Old Gen. Old Gen rises from 4 to 9 blocks. Clearing the cache removes its references. Old blocks become eligible once no references remain, and their space is still occupied until a collection that includes old.

The model allocates up to five requests per allocation step and pauses application work during its young GC. Real collectors handle different lifetimes, sizes, promotion policies, and pause phases. The illustrated 91.7% and pause values are properties of this toy workload. Modern region-based collectors can assign spaces differently.

See the static cache leak in Java

Imagine temporarily logging the result of each call in a static map for debugging. This field belongs to the loaded controller class, and each unique request ID adds another entry.

private static final Map<String, List<OrderDto>> DEBUG_RESPONSES =
    new ConcurrentHashMap<>();

// Inside the handler, just before returning:
DEBUG_RESPONSES.put(requestId, result);

As long as the controller class is loaded and this map holds the entries, they keep each response list, its DTOs, and their labels reachable. A fixed-size cache with eviction puts a bound on how many responses are retained.

Five terms you’ll see again

Open any card for a definition and an example from a web service.

Heap

The JVM memory area for objects and arrays. Think of it as shared workspace for your DTOs, lists, and services. A request’s local variable can hold a reference to an object in that workspace.

GC root

A starting point for tracing what the app can still reach, such as a reference in an executing thread’s stack. A loaded class can also lead the collector through its static fields. A static map can keep every cached DTO reachable long after the original handler returns. In the coffee shop, an open order ticket leads staff to the tray still needed for that order.

Stop-the-world (STW)

A pause during which application threads suspend for JVM work. Imagine the baristas all put orders down while the counter is cleared. A request can spend part of a pause waiting, plus extra time in any queue that builds up.

Minor vs. major GC

A minor or young collection focuses on newer objects, like emptying the cup bin. Major usually refers to work that includes older objects, like clearing the shelf. Terminology varies by collector. A full GC generally covers the entire heap. Look for the actual event name in the log.

Throughput vs. latency

Throughput is work per unit of time, such as total responses per second. Latency is how long a request takes. A shop can serve many cups per hour while its slowest customers wait a long time. Likewise, high request throughput can coexist with slow tail latency.

Spot a young collection in a real log

Run java -Xlog:gc -version to see which collector the JVM picks for that launch. To check your service, add logging to its own launch command, for example java '-Xlog:gc*' -jar app.jar. Look for a startup line such as Using G1. The event below came from the allocation exercise on Temurin 25.0.4.

[0.372s][info][gc] GC(2) Pause Young (Normal) (G1 Evacuation Pause) 18M->5M(32M) 0.675ms
[0.372s][info][gc]

The JVM was 0.372 seconds into this run. The log level is info and the tag is gc.

GC(2) Pause Young

Event 2 was a young collection. During this pause, G1 moved live objects out of selected regions so it could reuse those regions.

18M->5M(32M) 0.675ms

Used heap dropped from about 18 MiB to 5 MiB. Committed heap was about 32 MiB, and the application pause lasted 0.675 milliseconds.

Run the allocation example on JDK 25

Save this as GcRequests.java. Each iteration creates a 16 KiB payload and replaces the last one, leaving only the newest payload reachable through the field.

public class GcRequests {
    private static volatile byte[] latestPayload;

    public static void main(String[] args) {
        for (int request = 0; request < 10_000; request++) {
            latestPayload = new byte[16 * 1024];
        }
        System.out.println("Processed 10,000 simulated requests");
    }
}
java -Xms32m -Xmx32m -XX:+UseG1GC -Xlog:gc GcRequests.java

Expect a Using G1 startup line, several young collections, and Processed 10,000 simulated requests. Heap figures and timings vary between runs. The JVM and source launcher perform their own allocations too.

If the API slows down again, compare request timestamps with GC pauses in the same JVM and time window. If the request logs use wall time, use -Xlog:gc:stdout:time,uptime,level,tags to include it. Check CPU, queues, and upstream timings alongside the GC log.

Frequent young collections with a stable after-GC baseline can be ordinary allocation churn. A rising baseline after collections that reclaim old objects points toward growing retention.

The collector roadmap

A collector is the JVM’s implementation of garbage collection. Each trades off throughput, pause time, and memory footprint. Work done concurrently can keep request threads running while using some of the CPU and memory they share. The flags below are for JDK 25 HotSpot.

  • Serial GC

    -XX:+UseSerialGC

    One GC worker during pauses. A small single-CPU service or CLI can benefit from its low overhead. Larger collections may pause longer because one worker does the job.

  • Parallel GC

    -XX:+UseParallelGC

    Multiple GC workers collect during pauses. A nightly batch job can prioritize throughput when longer pauses are acceptable.

  • G1 GC

    -XX:+UseG1GC

    The typical server default. It divides the heap into regions, marks live data concurrently, and copies live objects out of selected regions during pauses. Its pause target is a goal.

  • Generational ZGC

    -XX:+UseZGC

    Moves objects concurrently to keep pauses short. Consider it when pauses matter and CPU and heap headroom allow collection to keep pace. JDK 24 removed the non-generational mode.

  • Generational Shenandoah

    -XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational

    Moves objects concurrently with low pauses as a goal. Use both flags to enable this mode on JDK 25 builds that include Shenandoah. Leave room for concurrent work and new allocations.

  • Epsilon

    -XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC

    Allocates memory without reclaiming it. Useful in bounded experiments, such as isolating collection costs. Continuing to allocate eventually exhausts the heap.

HotSpot typically selects G1 on server-class configurations and can select Serial on smaller ones. Check the startup log to see what your JVM picked. Older guides may mention CMS, which was removed in JDK 14.
