Follow a request through the heap

Think of a checkout API as a kitchen. Each order gets a prep tray. When the order goes out, its tray can be cleared. The recipe binder stays on the shelf because the next order still needs it.

What can be cleared?

The heap is the memory area where Java objects live. A collector follows references from known starting points called GC roots, such as references in live thread stacks. In this lesson we use ordinary strong references. If a root can reach an object, the collector must keep it.

A checkout handler creates a response object and a payload. When the request finishes, those objects can become unreachable and eligible for reclamation. If a long-lived cache still points to a payload, the collector must keep it even after the response is sent.

Why collect young objects first?

Many objects die soon after allocation. Generational collection groups objects by age so the JVM can collect the young generation frequently. Objects that survive enough collections may be promoted to the old generation. A young collection also accounts for references from old objects, including the cache in this lab.

      Read the worked heap trace

      Each slot holds one object. Survivors can move to old after their second young collection if there is room. The model uses fixed-size slots and collects only the young generation.

      1. Start with six objects. Young holds the response and payload from each of two requests. Old holds the cache and app configuration. Request 1 has finished, so its two objects are unreachable.
      2. Collect young. The collector reclaims request 1’s two objects. Request 2’s response and payload survive, leaving four occupied slots in total.
      3. Retain request 2’s payload in the cache and finish the request. Collect young again. The response is reclaimed and the payload survives a second time, so it moves to old. Three slots remain occupied.
      4. Clear the cache entries. The promoted payload is now unreachable, but it still occupies a slot. A collection that includes old can reclaim its space.

      The collector roadmap

      Every collector makes a different trade-off among throughput (requests or jobs completed per unit time), pause time (time application threads are stopped), and memory footprint. Concurrent phases overlap with application work and compete for resources. A stop-the-world phase suspends application threads.

      The six collector lessons are planned. The commands here use the JDK 25 HotSpot baseline.

      • Serial GC

        -XX:+UseSerialGC

        One GC worker during pauses. A small single-CPU service or CLI can benefit from its low overhead. Larger collections may pause longer because one worker does the job.

      • Parallel GC

        -XX:+UseParallelGC

        Multiple GC workers collect during pauses. A nightly batch job can prioritize throughput when longer pauses are acceptable.

      • G1 GC

        -XX:+UseG1GC

        The typical server default. It divides the heap into regions, marks live data concurrently, and copies live objects out of selected regions during pauses. Its pause target is a goal.

      • Generational ZGC

        -XX:+UseZGC

        Moves objects concurrently to keep pauses short. Consider it when pauses matter and CPU and heap headroom allow collection to keep pace. JDK 24 removed the non-generational mode.

      • Generational Shenandoah

        -XX:+UseShenandoahGC -XX:ShenandoahGCMode=generational

        Moves objects concurrently with low pauses as a goal. Use both flags to enable this mode on JDK 25 builds that include Shenandoah. Leave room for concurrent work and new allocations.

      • Epsilon

        -XX:+UnlockExperimentalVMOptions -XX:+UseEpsilonGC

        Allocates memory without reclaiming it. Useful in bounded experiments, such as isolating collection costs. Continuing to allocate eventually exhausts the heap.

      HotSpot typically selects G1 on server-class configurations and can select Serial on smaller ones. Check the runtime’s startup log to see what it picked. Concurrent Mark Sweep (CMS) was removed in JDK 14.

      Read your first GC log

      Start with the collector name. Run the command using the same JDK and runtime limits as the service. Look for a message such as Using G1 to identify the collector chosen for that launch. To verify a deployed service’s actual settings, add logging to its own startup command.

      java -Xlog:gc -version

      A G1 young collection

      Captured on Temurin 25.0.4 with the example below.

      [0.372s][info][gc] GC(2) Pause Young (Normal) (G1 Evacuation Pause) 18M->5M(32M) 0.675ms
      [0.372s][info][gc]

      The JVM had been running for 0.372 seconds when it logged this info-level GC event.

      GC(2) Pause Young (Normal)

      GC event 2 includes a stop-the-world young collection. During evacuation, G1 copies surviving objects out of the selected regions so it can reuse those regions.

      18M->5M(32M) 0.675ms

      Used heap fell from about 18 MiB to 5 MiB, with 32 MiB of committed heap. The application pause lasted 0.675 milliseconds.

      Connect the pause to the symptom

      Line up GC events with slow requests using timestamps from the same process and time window. A brief pause can contribute to request queuing. Also inspect CPU saturation and upstream latency before attributing a spike to GC.

      Compare heap usage after like-for-like collections under similar load. Frequent drops back to a stable level can indicate heavy temporary allocation. A rising baseline after collections that reclaim old objects can indicate a growing live set, such as an unbounded cache.

      Use -Xlog:gc* for more detail, including G1’s phase and heap summaries. When request logs use wall-clock timestamps, specify -Xlog:gc:stdout:time,uptime,level,tags to include both wall time and JVM uptime.

      Run the allocation example on JDK 25

      Save this as GcRequests.java. Each iteration creates a 16 KiB payload and replaces the last one, leaving only the newest payload reachable through the field.

      public class GcRequests {
    private static volatile byte[] latestPayload;

    public static void main(String[] args) {
        for (int request = 0; request < 10_000; request++) {
            latestPayload = new byte[16 * 1024];
        }
        System.out.println("Processed 10,000 simulated requests");
    }
}
      java -Xms32m -Xmx32m -XX:+UseG1GC -Xlog:gc GcRequests.java

      Expect a Using G1 startup line, several young collections, and Processed 10,000 simulated requests. Heap figures and timings vary between runs. The JVM and source launcher perform their own allocations too.

      Check your intuition

      A checkout finishes, but a shared map still holds its payload. Can GC clear it?

      The map keeps the payload reachable. Removing or evicting the entry makes it eligible once the last path from a root is gone.

      Heap usage climbs before each young collection and falls to roughly the same level. What might explain it?

      A burst of short-lived allocations can create that sawtooth pattern. To investigate long-lived retention, also inspect old-generation usage after collections that reclaim it.

      A nightly worker needs to finish more jobs per hour and can tolerate pauses. Which collector would you test?

      Parallel GC is a reasonable candidate on a multi-CPU host. Compare completed jobs per hour against the current collector at the same heap size, CPU limit, and input load.
