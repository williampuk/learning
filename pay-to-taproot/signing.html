Part 4

Key-path spends and signature hashing

Follow a node and a signer as they independently reconstruct the same transaction digest.

A payment from funding to signature

Alice derives a child key, tweaks it, and gives Bob a Bech32m address. Bob converts it to 51 20 <x(Q)> in a funding output and puts a value beside it. Alice’s spending input references that exact old TXID and output index. She selects the new outputs and fee, computes the Taproot digest, and signs with q. Her input has an empty scriptSig and normally carries one witness item.

How the node verifies Alice’s payment

  1. Find the UTXORead the old amount and scriptPubKey.
  2. Classify witnessRemove a trailing annex if present. One remaining item selects key path.
  3. Rebuild the digestUse the parsed sighash type and the transaction context.
  4. VerifyLift x(Q), verify Schnorr, then apply the transaction’s other consensus checks.

The node gets x(Q) from the previous output. The spending transaction may have completely different outputs. The witness leaves P, the optional root, and any control block undisclosed. The previous commitment already carries a valid public key for verification.

Ordinary key path, serialized witness
01 | 40 | <r:32> <s:32>
01 = 1 stack item; 40 (hex) = 64-byte item.

A 64-byte signature implies SIGHASH_DEFAULT. A 65-byte signature ends with one of the six defined nonzero hash types. Appending byte 00 to a 64-byte signature produces an invalid encoding. DEFAULT covers the same categories of data as ALL, but the first SigMsg byte differs and therefore the digest differs.

What exactly did Alice approve?

Think of the signing message as a receipt for the fields Alice authorizes. She cannot infer the fee from the unsigned transaction alone because input amounts live in previous outputs. BIP341 commits to the amounts and scriptPubKeys of every input when ANYONECANPAY is absent. Given trusted prevout data, an offline signer can identify input types, check amounts, and detect substituted data. BIP143 commits to the current input amount and a scriptCode with its own rules. BIP341 serializes a different message and uses single SHA-256 component hashes. The annex is covered by the signature but currently has no spending semantics. Relay policy may be more restrictive than the consensus example.

The script extension stops a signature made for one leaf from silently authorizing another leaf. The digest includes the leaf itself through its hash. An executed CODESEPARATOR adds execution-position context without replacing the committed script bytes.

Experiment J · Change the signing coverage

Rows appear in signing order. Open a subhash to inspect exactly which original bytes it covers. This modifies the message while retaining the original signature.

Check your understanding

Level 1 · Why are the amounts and old scripts visible to the signer?

Hint

Consider fee calculation and which script the signer is spending.

Worked solution

They provide the context necessary to check the payment and are part of the digest, so false prevout data cannot produce a network-valid signature for the true prevouts.

Level 2 · A witness has one 65-byte item ending 00. Which node step fails?

Hint

Check signature parsing before constructing SigMsg.

Worked solution

Taproot rejects the explicit zero type byte. DEFAULT is represented by omitting the byte from the witness signature. The constructed SigMsg still contains 00 in its hash_type field.

Level 3 · Why does SINGLE fail for the confirmed script-path input?

Hint

Look at input 1 and count outputs.

Worked solution

The input is index 1 and the transaction has only output index 0. There is no corresponding output to hash.
