Start from a spend you already know

Say Bob pays Alice. The funding transaction creates an output whose scriptPubKey describes what a future spender must prove. With P2WPKH, Bob’s output publishes a 20-byte fingerprint of Alice’s public key. Later, Alice spends it by revealing both the key and an ECDSA signature. The node checks the fingerprint and then the signature.

  1. Bob fundsOP_0 <20-byte key hash>
  2. Alice spendsECDSA signature + compressed key
  3. Node checksHASH160(key), then ECDSA

Keep the two views separate as you read. The bytes Bob publishes are the commitment. The bytes Alice supplies later are the evidence. Taproot changes both views, while keeping the same transaction model.

Output typeFunding scriptPubKeyEvidence in the spendWhat the node checks and what becomes public
P2PKH76 a9 14 <20> 88 acscriptSig [signature, key]HASH160 of the disclosed key, then ECDSA. The unlocking bytes are in the base transaction.
P2SHa9 14 <20> 87scriptSig [arguments…, redeem script]HASH160 of the redeem script, then execute it. For an ordinary non-witness redeem script, all policy branches become visible. A nested witness program has its own rules.
P2WPKH00 14 <20>witness [signature, compressed key]Version 0. HASH160 of the disclosed key, then ECDSA with the BIP143 digest. The format represents a single key hash.
P2WSH00 20 <32>witness [arguments…, witness script]Version 0. Verify SHA-256 of the entire disclosed script and then execute it. Alternative branches inside that script are visible.
P2TR51 20 <32>witness [signature] or [arguments…, leaf, control]Version 1. Verify Schnorr against the encoded output point, or reconstruct that point from the selected script and proof before applying the leaf’s rules.

In those layouts 14 and 20 are hexadecimal push lengths, 20 and 32 bytes. 00 is OP_0 and 51 is OP_1. The trailing P2PKH bytes are EQUALVERIFY and CHECKSIG.

The spending policy worth hiding

Alice and Bob want a shared vault. Normally both approve a payment. If Bob is unavailable, Alice uses a separate recovery key after 144 blocks. Three designated trustees hold separate keys. Any two can recover after 4,320 blocks. For the three-leaf tree later in the guide, a separate arbiter can sign once the chain passes an agreed absolute height. Block counts are measured in blocks. 4,320 is about 30 days at an average ten minutes per block.

A P2WSH witness script can encode the entire policy with conditional branches. Even when Alice and Bob cooperate, the node needs the entire script to check that it hashes to the funding program. The witness carries the unused branches, exposing keys and delays and consuming witness bytes. For a simple one-key payment P2WPKH is already compact. The disclosure problem is most visible when the policy has alternatives.

One output with two ways to spend

  1. Internal keyThe original public key, or a jointly controlled key.
  2. Optional script treeOne leaf per fallback condition. A single hash summarizes the tree.
  3. Output keyCombine the key and the tree commitment into a new key.
  4. On chainThe previous output stores only the 32-byte x coordinate of this key.

The organizational idea is to put the likely outcome on the key path. If cooperation fails, a script path reveals the selected rule and enough sibling hashes to prove it was committed. Think of the proof as directions from a specific leaf back to the same commitment the funder used. You will reproduce those directions and check the exact bytes in Part 5.

A cooperative witness alone is compatible with both a single signer and several cooperating signers, and with either presence or absence of a tree. A recovery witness reveals the chosen condition and proof depth. Common transaction clues such as amounts, timing, and address reuse remain visible. Taproot extends Bitcoin Script through a new leaf version, and existing output types keep their rules.

Check your understanding

Level 1 · What does an ordinary P2WPKH spend disclose that a cooperative Taproot spend omits?

Hint

Compare the witness item counts.

Worked solution

P2WPKH provides the key preimage for its HASH160. A Taproot key-path spend verifies against the output key already in the previous output.

Level 2 · Why can’t a P2WSH spender supply only one branch of its witness script?

Hint

Compare hashes of the full script and of the excerpt.

Worked solution

The funding commitment is SHA-256 over every serialized script byte. Hashing the selected branch yields a different digest.

Level 3 · Select each real witness in the comparison. Where are the policies or keys?

Hint

Look at the last item and its byte count.

Worked solution

The 33-byte P2WPKH item is a compressed public key. The P2WSH last item is a 105-byte multisig script. The P2TR key-path witness has only the 64-byte signature.
