Why a linear signature helps

Alice’s one-key wallet needs an ordinary signature. Alice and Bob’s vault would benefit from both people authorizing the same payment while seeing only one public key and one signature on chain. Schnorr’s equations give a secure coordination protocol something to build on. Start by writing down what changes relative to ECDSA.

ECDSA:   R = kG    r = x(R) mod n    s = k⁻¹(z + r·d) mod n
Schnorr: R = kG    r = x(R)          e = int(H_challenge(r || x(P) || M)) mod n
                                     s = (k + e·d) mod n

G is the public secp256k1 generator and n is its order. The signer owns scalar d and uses fresh private nonce scalar k. P = dG is the public point and R = kG is the nonce point. For ECDSA, z is the signing hash interpreted as an integer. For BIP340, M is the message byte string, e is the public challenge, and r and s are encoded as 32-byte big-endian integers. The challenge hashes encoded values of r and x(P), each 32 bytes. Schnorr’s r is a field coordinate, so r < p, where p is the field modulus. ECDSA reduces its coordinate modulo n.

  1. Compute a nonce pointR = kG
  2. Bind the contextHash R’s x coordinate, the public key, and the message.
  3. RespondAdd the nonce scalar to e times the normalized signing scalar.
  4. VerifyMultiply the response by G and reconstruct R. 
sG = ((k + e·d) mod n)G
   = kG + e(dG)          because nG = ∞
   = R + eP
R′ = sG − eP             verifier reconstructs the nonce point

The verifier knows s, e, P, and G. It checks that the reconstructed point has the specified x coordinate and even Y. The same additive relationship is why coordinated partial responses can be combined in MuSig2. ECDSA signatures solve a different equation and cannot be converted into BIP340 signatures. Replacing Schnorr’s s with n−s changes the equation. BIP340 neither calls for Low-S normalization nor accepts both signs by convention.

If k is reused with the same normalized signing key, subtract two valid equations: s₁ − s₂ = (e₁ − e₂)d mod n. When the challenges differ, inversion reveals d. Cross-protocol nonce reuse can also leak a shared secret. Use scheme-specific, audited nonce generation and avoid allowing a caller to choose arbitrary signing nonces.

For the toy calculation we use the actual curve y² = x³ + 2x + 2 mod 17, with generator (5, 1) of order 19. The toy challenge is addition modulo 19. Bitcoin uses tagged SHA-256 and secp256k1. With raw d₀=2 and k₀=3, the normalized scalars are d=17 and k=3, giving P=(6,14) and R=(10,6). For message integer 4, e=1, s=1, and both sides equal (5,1).

How to recover the point from 32 bytes

A compressed SEC1 public key includes a prefix that tells you which Y coordinate to use. Schnorr can agree ahead of time to use even Y. On secp256k1, points that share X are (x, y) and (x, p−y), since both have the same square modulo p. Because p is odd, their Y parities are opposite. The pair is one point and its group inverse.

c = (x³ + 7) mod p
y₀ = c^((p + 1)/4) mod p
Reject if x ≥ p or y₀² mod p ≠ c.
lift_x(x) = (x, y₀) if y₀ is even; otherwise (x, p − y₀).

Here c is the right-hand side of the curve equation. The exponent is integral because secp256k1’s field modulus p is 3 mod 4. Check the candidate square before accepting it. X arrives as a public big-endian 32-byte word. With raw secret d₀, the matching normalized scalar is d₀ if raw d₀G has even Y, or n − d₀ otherwise. Thus (n − d₀)G = −d₀G. Do the same for the nonce so that x(R) identifies the nonce point the signer used.

Ethereum’s ECDSA recovery yParity helps select a nonce-point candidate during recovery. The BIP340 public key convention chooses the even representative of a key. The Taproot control block later records the parity of a different point, the recomputed output Q.

Even representative

P = (x, y_even)

Encode x. Lift it back to this point.

Opposite point

−P = (x, p − y_even)

Same encoded x. Scalar multiplication switches from d to n−d.

Sign and verify an official BIP340 vector

Alice’s signer can reproduce the following vector from the message, private key, and auxiliary bytes. Auxiliary randomness hedges the signing process. The official all-zero aux example illustrates deterministic reproducibility. For deployments, the signer should follow the documented randomness and side-channel requirements.

H_tag(X) = SHA256(SHA256(UTF8(tag)) || SHA256(UTF8(tag)) || X)
a = H_BIP0340/aux(aux32)
u = bytes32(d) XOR a
k₀ = int(H_BIP0340/nonce(u || x(P) || M)) mod n
k = k₀ if k₀G has even Y, else n − k₀
r = x(kG);  e = int(H_BIP0340/challenge(bytes32(r) || x(P) || M)) mod n
s = (k + e·d) mod n;  signature = bytes32(r) || bytes32(s)

The signer rejects a raw secret outside [1, n−1] and a zero k₀. The 32-byte value a is the tagged hash of the auxiliary bytes. The masked secret u, raw nonce hash, and private k values stay inside an actual signing boundary. The published test vector can display them. Tags give separate hash domains to otherwise ambiguous byte streams. Verification lifts x(P), checks lengths and ranges, computes e independently, and rejects infinity, odd Y, or x(R′) unequal to r.

Check your understanding

Level 1 · Why can the verifier reconstruct R from x(P) without a key prefix?

Hint

Find the parity selected by lift_x.

Worked solution

The protocol always interprets x(P) as the even-Y point, and the signer normalizes d accordingly.

Level 2 · Take d₀=2, k₀=3 and change the toy message from 4 to 5. What is s?

Hint

Only e and s change.

Worked solution

e = (10+6+5) mod 19 = 2. The response is (3+2·17) mod 19 = 18. The verifier reconstructs (10,6).

Level 3 · Open BIP340 vector 0. Which 32 bytes encode the response?

Hint

Read the split r || s.

Worked solution

The trailing 32 bytes, beginning 25f66a4a, are s. The first 32 bytes, beginning e907831f, are the nonce coordinate.
