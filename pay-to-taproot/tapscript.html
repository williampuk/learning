A proven script still needs to pass

The recovery witness proves that the funder committed to some bytes. Those bytes still have to authorize this transaction. With leaf version c0, Bitcoin evaluates them under BIP342. A one-key recovery rule can check a Schnorr signature. A quorum rule can count successful checks directly. Both use the script-path digest from Part 4.

For a known 32-byte key, an empty signature gives false (or adds zero), and an invalid nonempty signature fails immediately. A zero-length public key fails. Unknown nonzero key lengths have an upgrade behavior for nonempty signatures and still consume budget. OP_SUCCESSx encountered while decoding an opcode makes a c0 script succeed immediately under current rules, even in an unexecuted branch. It is distinct from the same byte inside pushed data. Avoid relying on one as a restriction. This eager success can bypass checks including normal initial-stack limits. Future soft forks can assign stricter semantics.

Alice’s delayed recovery

Alice needs a signature that cannot spend immediately if Bob is unavailable. Set transaction version at least 2, sequence disable bit 31 clear and type bit 22 clear for block units, and low 16 bits at least 144. CSV enforces the transaction-level requirements. BIP68 separately enforces age against the chain: with sequence 144 and confirmation at height H, the earliest possible spending block is H+144. Setting a larger sequence can require additional blocks.

<144> CHECKSEQUENCEVERIFY DROP <x(AliceRecovery)> CHECKSIG
02 90 00 | b2 | 75 | 20 <32 bytes> | ac

The first ScriptNum is little-endian signed-magnitude. 0x90 needs a trailing 00 to keep it positive. CSV reads but leaves the stack top, so DROP removes the delay before the key is pushed. The same policy in P2WSH can use a compressed public key and ECDSA. When wrapped inside a multi-branch P2WSH policy the whole witness script is disclosed. The vault’s Taproot cooperative spend leaves this script hidden.

The trustee quorum uses three signature slots

Leaf B first enforces a delay of 4,320 blocks and drops the delay value, using the same mechanism as Leaf A. Then it counts approvals. Trustees A, B, and C in this section are three separate people holding distinct script keys. They are independent of Alice and Bob’s cooperative keys.

<x(A)> CHECKSIG <x(B)> CHECKSIGADD <x(C)> CHECKSIGADD 2 NUMEQUAL
Initial recovery witness arguments, bottom → top: [sig_C, empty, sig_A]

The first CHECKSIG pops key and signature, producing a count of one for trustee A. For each CHECKSIGADD, the popped values from top down are key, numeric accumulator, signature. An empty signature is a zero-byte item (its witness length is 00). It contributes zero. Signer C adds one, then the script compares the count to 2. This exact-equality policy requires exactly two successful slots, so a wallet with all three approvals chooses two for the witness. Everyone can see the full set of three keys and which two slots carried signatures.

Step through both recovery stacks

The vault fixture contains the fully signed delayed and quorum inputs. The Go program verifies both with a script engine, and also signs a sequence-143 attempt that fails at CSV.

Check your understanding

Level 1 · What happens if a signer places an invalid nonempty signature in a slot?

Hint

Separate empty from invalid.

Worked solution

For a 32-byte key, BIP342 fails immediately on a nonempty invalid signature. Leave an absent signer’s slot empty so CHECKSIGADD adds zero.

Level 2 · Why is a compressed key serialized differently in the P2WSH version?

Hint

Which signature rules run for each version?

Worked solution

P2WSH uses SEC1 compressed keys for ordinary standard ECDSA spends. Tapscript uses the 32-byte x-only BIP340 key. The stack policies can otherwise have the same CSV intent.

Level 3 · If Alice’s UTXO confirmed at height 900000 and her nSequence is 144, when can the spend be mined?

Hint

Check BIP68 separately from CSV.

Worked solution

Earliest height 900144. A correctly signed transaction with nSequence=143 still fails CSV, and a 144 sequence can pass script execution while failing age validation in an earlier block.
