Agree on exactly what the vault authorizes

Build this vault before looking at the results below. Alice and Bob own separate cooperative keys and both are required in MuSig2. Alice has an independent recovery key with a 144-block delay. Three trustees each control another key, and any two can recover after 4,320 blocks. A designated arbiter with a separate key is an optional third leaf, enabled by an absolute locktime of block 1,000,000. These are public fixture keys for practice.

  1. Compute the BIP327 aggregate from the two participant keys. Take its x coordinate and lift to even Y to obtain P.
  2. Build the scripts, calculating CompactSize of each script and hashing c0 || length || script for each leaf.
  3. Pair B and C by sorted TapBranch. Pair the result with A to form m. This keeps the more likely recovery rule shallow.
  4. Hash x(P) || m under TapTweak, interpret it as t, and compute Q. Encode p2tr scriptPubKey and Bech32m address from x(Q).
  5. Simulate two distinct 100,000-sat deposits to that same scriptPubKey. Each withdrawal makes a 99,000-sat output and leaves a 1,000-sat fee. The Go fixture makes each synthetic funding transaction distinct.

Sign two independently funded withdrawals

Cooperative withdrawal

Make a version-2 transaction with final sequence and empty scriptSig. Compute DEFAULT key-path digest. Alice and Bob exchange public nonces and use a tweaked MuSig2 session to build the signature for Q. The witness is one 64-byte signature. Verify it against x(Q).

Delayed recovery

Use version 2 and nSequence 144. For a funding confirmation at height 900,000, spend at 900,144 or later. Compute the DEFAULT Tapscript digest for A. Sign with the recovery key and append Leaf A and its control block. The node reconstructs Q and its parity, then checks CSV and the signature.

For Leaf B, spend at sequence 4,320 and supply signatures from trustees 13 and 19 with an empty slot for 17. The proof uses L_C and then L_A. For C, use nLockTime 1,000,000 and a non-final input sequence. With this height-based locktime the spending block must be above 1,000,000. Both alternative script paths are present in the worked fixture.

Inspect commitment, witness, and signature checks

The browser independently rebuilds the aggregate key, tree, tweak, and each selected transaction’s digest. It checks applicable signatures and proofs, and shows the cooperative public nonce exchange and partial responses. The Go program runs the script interpreter. It uses synthetic prevouts, so confirmation-age checks are explained against the stated block-height scenario.

The first two transactions are 444 WU and 550 WU. Recovery adds the 39-byte leaf, the 65-byte control block, and one prefix for each. Both have the same number of base bytes and one output. Key path discloses one signature. Recovery discloses Alice’s recovery key and delay, internal x(P), and a hash of the hidden B+C subtree. Both satisfy the same output program on their own UTXOs.

Check your understanding

Level 1 · Why fund two independent outputs for this comparison?

Hint

What would happen if the two transactions referenced the same outpoint?

Worked solution

They would conflict. Separate outpoints with the same scriptPubKey let you compare valid spending methods without attempting to spend the same coin twice.

Level 2 · Compute the control-block size for B and state its sibling order.

Hint

Walk from B up to the root.

Worked solution

First C’s leaf hash, then A’s. Two siblings produce 33+64 = 97 bytes, including the header and internal key.

Level 3 · Change the delay to 145 and try to reuse the old commitment. Which tests fail?

Hint

Consider both membership and the script’s signature digest.

Worked solution

The script byte change changes Leaf A’s hash, then the root and x(Q). The original UTXO commitment cannot authorize the new script. If you fund a new output for that script, sign a fresh digest and raise the sequence.
