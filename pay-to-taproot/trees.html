Why keep fallback policies in a tree?

If Alice and Bob can both approve today, the key path suffices. The point of the vault is to remain usable if a signer is unavailable. A delayed recovery leaf grants Alice recovery while giving the normal operators time to respond. In an inheritance policy, estate trustees can act under a delay. In escrow, a designated adjudicator can resolve a dispute when the ordinary parties stop cooperating. A leaf describes a spending rule, and every path you add is another way control can be exercised.

There is a key-path rule for every valid output key. Practical access depends on whether anyone knows or collectively controls its secret. A script-only design can use a convincingly generated point with no known discrete logarithm for P. Knowing the public tweak then gives no known secret for Q either. BIP341 discusses verifiable NUMS internal keys and an optional randomized construction. A key-path spend cannot prove whether any hidden tree originally existed.

m = Branch(L_A, Branch(L_B, L_C))

A script S is a public byte string when revealed. Version v is the single byte c0 for Tapscript. It belongs in the hash so changing the interpretation changes the commitment. Length is an integer serialized as CompactSize. With OP_1 (51) the exact data after the tag prefix is c0 01 51. With a 253-byte script the length prefix is fd fd 00. The branch inputs a and b are each 32-byte child hashes. Bounds or comparisons on these bytes use lexicographic order, with the first unequal unsigned byte deciding.

Swapping siblings within one branch keeps the root. Moving a leaf to a different pair generally changes the root. A single leaf is itself the root. A valid tree can be unbalanced. With A at depth 1, revealing A costs one sibling while revealing B costs two. Placement can favor the path most likely to be used, at the cost of different disclosure and witness sizes.

Bind the tree to one output

The root m is a compact receipt for the whole tree. Append its 32 bytes to x(P) before TapTweak. A new delay changes script bytes, the leaf hash and every ancestor on its route to the root. Adding or removing a leaf changes that recipe too. Replacing P changes the tweak’s first 32 bytes even if the script tree stays identical. In all cases the derived x(Q) generally changes and so does its Bech32m address.

What the spender actually reveals

Script-path witness = [arguments…] [revealed script] [control block] [optional annex]
Control block       = [header:1] [internal x(P):32] [sibling 1:32] … [sibling d:32]

After removing a recognized annex, two or more remaining items use the script path. The last is control, the previous one is the script, and earlier items form the initial stack. For the capstone’s Leaf A, the lengths are 64 bytes for a DEFAULT signature, 39 bytes for the script, and 65 for control. Each element has a CompactSize length prefix and the witness begins with its item count. A P2WSH witness includes the whole witness script and no Merkle proof.

The control block is a proof recipe

0
Leaf version and parity
1–32
x(P)
33–64
Sibling nearest the leaf
65 onward
Higher siblings, 32 bytes each

The first control byte is leaf_version | (y(Q) & 1). Decode version with & 0xfe and parity with & 1. The parity is from the full output point Q, independent of the internal key’s even-Y lift and the Schnorr nonce’s parity. BIP341 includes this bit so a verifier can reconstruct one specific output point for batch verification. With d sibling hashes, size is 33 + 32d bytes for depth 0 through 128. Here d means depth only. The signing scalar d used elsewhere is a different quantity.

The internal key is necessary to reconstruct the tweak and Q. The nearest sibling comes first, because each new parent becomes the accumulator at the next level. Left versus right at the same level is immaterial after sorting. Swapping two levels in the proof generally fails. A valid proof exposes the path length, leaf version, a key, and hashes of sibling subtrees. The hashes do not give the scripts, but a known or guessable subtree can be tested against a revealed hash.

Membership comes before policy satisfaction

  1. Parse witnessFind the prevout program, remove annex if present, then extract script and control.
  2. Prove membershipCheck control length and leaf version. Hash the revealed leaf, fold siblings, lift P, and reconstruct Q.
  3. Check x and parityCompare x(Q) with the prevout and parity with the header.
  4. Apply the leaf rulesFor c0 execute Tapscript and validate signatures, timelocks, and final stack.

Wrong script bytes, wrong sibling bytes, or a wrong sibling order fail reconstruction. Wrong parity can fail even when x(Q) matches. Once the commitment passes, bad arguments or a bad signature fail execution. An unassigned leaf version that passes commitment checks currently succeeds under consensus. Default relay policy can still reject it. A future soft fork can define tighter rules for it. The interactive proof verifier checks the membership stage. The experiment below and the Tapscript chapter explain the execution stage.

Level 1 · What does the low bit of a control block encode?

Hint

Which point is reconstructed from the tree?

Worked solution

It is the parity of the full tweaked output point Q. The other parity conventions apply to different points.

Level 2 · In A beside (B,C), reconstruct the root from Leaf C.

Hint

Begin with C’s TapLeaf hash and use the nearest sibling.

Worked solution

Combine L_C and L_B with sorted TapBranch first. Then pair the resulting branch hash with L_A, again sorting the two inputs.

Level 3 · Load the real OP_1 leaf. Why is its control block 33 bytes?

Hint

Count its siblings and inspect its script.

Worked solution

There is a header and one 32-byte internal key, with zero siblings. Leaf hash equals root. The script pushes true without a witness argument.
