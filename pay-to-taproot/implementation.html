Go: Sign Alice’s key path and verify it locally

A software wallet assembles a transaction, retrieves its prevouts, signs the digest, and builds the witness. Splitting these jobs exposes which library function performs which part of the protocol. The bundled Go module uses pinned btcd and btcec packages. Its keys and fake funding transactions are public test artifacts.

cd pay-to-taproot/go
go run .

The program prints the signed wire transactions, outpoints, witnesses, hashes and sizes. It verifies each input with btcd’s script engine and checks the standalone key-path Schnorr signature. Download main.go, go.mod, and go.sum. Put the three files in one directory when running the downloads.

  1. Import scalar 3 with btcec and derive its public point. schnorr.SerializePubKey returns x(P).
  2. ComputeTaprootKeyNoScript lifts the key and adds TapTweak(x(P))·G. PayToTaprootScript emits 51 20 x(Q).
  3. The example constructs a synthetic funding transaction, then spends one 100,000-sat output into a 99,000-sat output. MultiPrevOutFetcher supplies the amount and script for hashing.
  4. CalcTaprootSignatureHash constructs the DEFAULT digest. TweakTaprootPrivKey handles internal parity and adds t. schnorr.Sign handles final BIP340 parity. The helper uses crypto/rand and schnorr.CustomNonce to choose the auxiliary-randomness nonce path.
  5. Place the 64-byte signature in the witness. Check the signature and run txscript.NewEngine with StandardVerifyFlags against the old output.
alice := demoKey(3)
	// BIP86-style commitment: hash x(P) alone and add tG.
	output := txscript.ComputeTaprootKeyNoScript(alice.PubKey())
	script := must(txscript.PayToTaprootScript(output))
	s := newSpend(1, script, wire.MaxTxInSequenceNum)
	digest := s.digest()
	tweaked := txscript.TweakTaprootPrivKey(*alice, nil)
	sig := sign(tweaked, digest)
	if !sig.Verify(digest, output) {
		panic("key-path signature failed independent Schnorr verification")
	}
	s.tx.TxIn[0].Witness = wire.TxWitness{sig.Serialize()}
	require(s.validate())
	result := s.report(digest)
	result["internalKey"] = h(publicKey(alice))
	result["outputKey"] = h(schnorr.SerializePubKey(output))
	result["scriptPubKey"] = h(script)
	result["regtestAddress"] = must(btcutil.NewAddressTaproot(schnorr.SerializePubKey(output),
		&chaincfg.RegressionNetParams)).EncodeAddress()
	return result
}

The local engine checks the script and signatures. Bitcoin Core regtest also supplies chain and mempool context. Open the reproduction below to test the same policy before and after the relative lock matures.

Go: Build a tree and sign the recovery leaf

The vault uses NewScriptBuilder for each rule, including minimal script-number bytes. NewBaseTapLeaf chooses c0. The library hashes that version, script length, and script. NewTapBranch sorts its two child hashes for each hash calculation. The tree shape is explicitly A beside (B,C). A control block for A therefore contains the internal key and a single proof hash for B+C. We deliberately reconstruct and check the commitment before constructing the signed witness.

a := txscript.NewBaseTapLeaf(delayed)
b := txscript.NewBaseTapLeaf(quorum)
c := txscript.NewBaseTapLeaf(emergency)
branch := txscript.NewTapBranch(b, c)
root := txscript.NewTapBranch(a, branch).TapHash()
output := txscript.ComputeTaprootOutputKey(internal, root[:])
// Build/serialize the control with internal key, output parity, c0, and branch hash.
// Independently verify it against x(Q) and the revealed script.
digest := s.scriptDigest(a) // CalcTapscriptSignaturehash adds the BIP342 extension.
sig := sign(recovery, digest) // Fresh auxiliary randomness, then BIP340.
s.tx.TxIn[0].Witness = wire.TxWitness{sig.Serialize(), delayed, controlBytes}

The script signature uses Alice’s dedicated recovery scalar directly with BIP340 normalization. Its key in the script is x(AliceRecovery), so adding the output tweak to that secret would sign for the wrong key. Run the program to see the key path, the delayed path, the CHECKSIGADD quorum path, and an absolute locktime path. For comparison it also correctly signs an input with sequence 143 and records the script engine’s CSV rejection.

Move transaction context across a signing boundary

A coordinator may assemble the unsigned transaction and ask a separate signer to approve it. A digest alone has discarded the context the signer needs. PSBT carries that context in maps. BIP371 adds fields for selecting and validating the particular Taproot path, in both PSBTv0 and PSBTv2.

Input PSBT fieldContent and use
0x13 TAP_KEY_SIGA 64- or 65-byte signature for the tweaked output key, returned by the signer.
0x14 TAP_SCRIPT_SIGMap keyed by x-only pubkey || leaf hash, with the signature as value. A leaf hash identifies which digest extension was signed.
0x15 TAP_LEAF_SCRIPTControl block as key data, script bytes followed by leaf version as the value. Gives the signer a proof it can verify against the prevout.
0x16 TAP_BIP32_DERIVATIONKeyed by x-only public key. Value has count and leaf hashes, then fingerprint and derivation path. Internal keys have zero associated leaf hashes.
0x17 TAP_INTERNAL_KEY32-byte x-only internal key.
0x18 TAP_MERKLE_ROOTOptional script-tree root, needed when recomputing a scripted policy’s output tweak.

A witness UTXO supplies the amount and locking script. For non-ANYONECANPAY the signer needs appropriate prevout data for every input. Output fields can provide an internal key, a serialized tree (depth, leaf version and CompactSize-prefixed script in depth-first order), and derivation metadata. MuSig2 session metadata is separate (BIP373). Independently verify outpoints, scripts, amounts, recipients, change, fee, authorized sighash type, key origin, and the recomputed output or proof. Finalization builds the actual witness from the collected signatures and path data.

An HSM needs the signature scheme and the correct key

Suppose Alice’s internal key is inside a PKCS#11 HSM such as a Thales Luna device. secp256k1 support describes the curve. The ECDSA signing mechanism produces an ECDSA response governed by an inverse nonce equation, while BIP340 needs the linear Schnorr response and specific challenge and parity rules. Prehashing the message or re-encoding the ECDSA output cannot supply a valid BIP340 signature. An ECDSA-only interface cannot sign a Taproot key-path input using ordinary ECDSA calls.

Key path

Compute Q publicly from x(P) and the committed root. The protected signer needs documented BIP340 signing and a way to normalize and apply the scalar tweak inside its trusted boundary, or an intentionally provisioned output-key signing capability. With multiple participants it needs the chosen secure signing protocol and tweak support.

Script path

An HSM-backed leaf key needs BIP340 for the leaf digest and normal even-Y normalization. It generally signs for the public key inside the leaf, with no TapTweak applied to that leaf key. The host still proves that the leaf belongs to the intended output.

A signer should know what it authorizes, verify that its selected public key matches the approved policy, and use a vetted BIP340 nonce implementation. MuSig2 nonces require separate session handling and one-time use. Exporting a long-lived scalar to tweak it in application memory defeats the hardware boundary and exposes the internal key through crashes, logs, or memory access. A leaked tweaked scalar with the public tweak and parity can also expose the internal scalar.

Check the mechanism list and documentation for the exact HSM model, firmware, policy mode and vendor extension, then confirm published test vectors with that device. This guide treats Luna as an integration scenario and makes no claim of BIP340 capability for any Luna model. Thales Luna Network HSM 7 SDK reference.
