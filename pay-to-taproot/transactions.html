A confirmed key-path payment

Start at input 0 of 33e794d097969002ee05d336686fc03c9e15a597c1b9827669460fac98799036 in block 709,635. It spends 88,480 sat from output 1 of 5849051c…f1d1. This transaction pays 67,230 sat to another P2TR output and has a zero-value OP_RETURN output with a message. The input-output difference is 21,250 sat.

Previous scriptPubKey
51 20 339ce7e165e67d93adb3fef88a6d4beed33f01fa876f05a225242b82a631abc0
scriptSig: empty
Witness stack: [64-byte signature]
Sighash: DEFAULT (no appended byte)

The witness contains one item, no annex, so the node uses the key path and verifies against the previous output’s x coordinate. You can learn which key the signature verifies under and which transaction fields it commits to. You cannot recover the internal key, signer count, or whether there were any fallback scripts from this witness alone.

A confirmed script-path spend with a one-level proof

In the same block, 37777defed8717c581b4c0509329550e344bdc14ac38f71fc050096887e535c8 spends two 491,750-sat outputs from one funding transaction. It creates a single 965,300-sat P2WPKH output. Input 0 uses the key path. Input 1 uses a 64-byte signature as a stack argument, a 34-byte Tapscript, and a 65-byte control block.

Script: 20 <32-byte x-only public key> ac
Control: c0 | <32-byte internal key> | <32-byte sibling>
TapLeaf data: c0 22 20 <32-byte x-only public key> ac

20 pushes the script’s public key, which may differ from the internal and output keys. ac checks the supplied signature under that leaf key. This leaf authorizes one signature with no timelock or threshold. The control block supplies just one sibling and the value c0 indicates even Q. The experiment reconstructs the root and Q, then uses the script extension to build the digest and check the signature.

Decode the disclosed public keys and signature format

The P2WPKH witness gives this compressed public key as its second item. Version 0 validates HASH160 of those 33 bytes against the previous 20-byte program.

026e5628506ecd33242e5ceb5fdafe4d3066b5c0f159b3c05a621ef65f177ea286

The first item ends with the sighash byte 01. Its earlier bytes are an ECDSA DER sequence: 30 44 wraps two INTEGERs, each 02 20 followed by 32 bytes. The BIP340 item uses two fixed-width words and omits the type byte for DEFAULT.

Input witness sizes include item counts and lengths. Overall transaction sizes also depend on every other input, output and script. The P2TR key-path transaction here has a smaller input witness than the P2WPKH transaction, yet a larger total size. In the controlled vault comparison, base transaction shapes match. The exact fee still depends on feerate.

Independent reproduction starts with the block and raw transaction bytes, available through your node or an explorer. The browser reconstructs serialized transactions from bundled records and verifies their Taproot signatures. For a historical lookup in Bitcoin Core, provide a block hash to getrawtransaction or use a transaction index. An independently downloaded previous transaction lets you extract the exact satoshi amounts and scripts yourself.

Check your understanding

Level 1 · Can the native type of the input be inferred from the spending outputs?

Hint

Which transaction supplied the locking script?

Worked solution

Take the input’s outpoint and read that previous output. The destination output can have a wholly different type.

Level 2 · What would the signing program have to change if a trailing annex were appended?

Hint

Check spend_type and the annex subhash.

Worked solution

It adds 1 to spend_type and inserts SHA256(CompactSize(length)||annex). The old signature would not verify against the changed digest.

Level 3 · Locate the signature check for input 1 of 37777d…35c8. What key is it under?

Hint

Read the 32 bytes immediately after script opcode 20.

Worked solution

It verifies against f5b059b9a72298ccbefff59d9b943f7e0fc91d8a3b944a95e7b6390cc99eb5f4, the leaf’s key. The funding program and control parity are verified in a separate commitment check.
