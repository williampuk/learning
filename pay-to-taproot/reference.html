Transaction and witness reference

Stripped TX: version[4] | #vin | vin… | #vout | vout… | locktime[4]
SegWit TX:   version[4] | 00 01 | #vin | vin… | #vout | vout… | witnesses… | locktime[4]
TxIn:  reverse(txid)[32] | index[4] | varbytes(scriptSig) | nSequence[4]
TxOut: satoshis[8] | varbytes(scriptPubKey)
Witness per input: item_count | varbytes(item_0) | varbytes(item_1) | …
Native P2TR scriptSig: 00 (length zero)
Key path: one remaining item after annex removal
Script path: arguments… | leaf script | control block, then any annex

Fixed-width numbers here use little-endian wire order. TXIDs are conventionally displayed with reversed digest bytes. Counts, script lengths, and witness item lengths use CompactSize: use one byte below 253, then prefixes fd/fe/ff plus 2/4/8 little-endian bytes as needed. Transaction weight is four times stripped size plus additional bytes from witness serialization, including marker and flag. Virtual size rounds weight/4 up.

From a spending rule to the node’s decision

  1. Choose authorityAn internal key for the normal case, plus optional recovery scripts.
  2. CommitTapLeaf and TapBranch give a root. TapTweak binds it to the key.
  3. PayEncode x(Q) into a version-1 program and Bech32m address.
  4. SpendSign for the output key, or reveal one script with a proof.
  5. ValidateUse the prevout. Reconstruct the digest and check the appropriate signatures and conditions.

BIPs 340, 341 and 342 specify the signature and Taproot spending rules. Bech32m and BIP86 specify address and wallet conventions. PSBT is interchange metadata. MuSig2 is an off-chain signing protocol. Relay policy can be tighter than consensus, especially for upgrade hooks. Bitcoin’s verifier can check a key-path signature without learning any construction history.

Common misconceptions

“P2TR is just P2WPKH with a new prefix.”

Its witness program contains a 32-byte output point coordinate. It uses v1 validation and a different signature scheme, with an optional script path.

“It still uses ECDSA because it uses secp256k1.”

BIP340 and ECDSA use the same group with different signature equations.

“Internal and output keys are the same.”

The internal even point P is an input to TapTweak. Q adds a public offset and is the key encoded in the UTXO.

“A tweak is random.”

It is deterministic from the x-only internal key and the optional Merkle root.

“The address is SHA256(pubkey).”

Bech32m encodes the version and actual 32-byte x(Q) witness program.

“The original private key can sign unchanged.”

Key-path signing uses the normalized internal scalar plus tweak and a final even-Y adjustment.

“Every spend reveals a script.”

Ordinary key path publishes one signature.

“All P2TR spends are multisig.”

Alice’s one-key wallet is P2TR too.

“Taproot automatically combines signatures.”

A coordinated protocol such as MuSig2 generates a joint signature. Independent signatures carry different challenges.

“MuSig2 is a P2TR consensus rule.”

The node verifies an ordinary BIP340 signature. How the wallet generated it is off chain.

“A Merkle root identifies the script without a proof.”

The verifier needs the leaf bytes and sibling hashes to reconstruct the committed root.

“Control contains the whole tree.”

It carries the header, internal key, and one hash per sibling subtree.

“Control parity equals ECDSA recovery yParity.”

Control records parity of full Q. ECDSA recovery uses a nonce-point candidate parity.

“Key path proves no script tree existed.”

The witness has the same shape either way.

“Taproot makes transactions private.”

Key path hides the unused policy. The amounts, input graph, and funding and spending times remain observable.

“An ECDSA signature can be converted into Schnorr.”

Changing the format does not change the signing equation or supply the new secret response.

“Every Taproot signature item is 64 bytes.”

Non-default sighash types append one byte. Empty signature slots in Tapscript are possible too.

“Any secp256k1 HSM can sign Taproot.”

The device needs the appropriate BIP340 functionality and a way to sign under the intended key.

“The seed is always enough.”

A complex vault can require separate keys, script bytes, a proof or tree, participant order, and derivation metadata.
