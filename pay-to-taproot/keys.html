From an internal key to an address

Why publish Q instead of P?

Suppose Alice funds an output using just the public key she already has. Anyone who knows the key can verify an ordinary signature. But the same 32 bytes would be used whether Alice intended a recovery rule or a completely different one. A node would have no way to tell which rule, if any, was authorized by the funding output.

Taproot needs a key that still behaves like a key when checking a signature, but can also encode a commitment. Start with Alice’s even-Y internal point P. Compute a public offset from the key and the optional script root. Add that offset as a point. The result Q still has a corresponding private scalar. An outside observer who knows the ingredients can repeat the public calculation.

  1. Internal PLift its 32-byte X to the even-Y point.
  2. Public offset tHash x(P) and any script root under TapTweak.
  3. Point tGMove by t multiples of the generator.
  4. Output QAdd P + tG and encode only x(Q).

On the toy curve from Part 2, take normalized d=17 and imagine the hash provided t=5. The public result is 17G + 5G = 22G = 3G = (10,6), since the group order is 19. The corresponding scalar is (17 + 5) mod 19 = 3. Here t=5 is an input to illustrate the addition. The live Bitcoin example computes t with real SHA-256.

The bytes that bind the output

X = x(P)               when no script tree is provided
X = x(P) || m          when a script tree is provided
t = int(H_TapTweak(X))
Q = P + tG

The internal x coordinate is a public 32-byte big-endian serialization. The root m is a 32-byte public-when-disclosed hash from Part 5. It is omitted entirely in the single-key case. A 32-byte all-zero root is different from an omitted root. The tweak hash is interpreted as an unsigned big-endian scalar. BIP341 rejects t ≥ n rather than reducing it, and rejects the point at infinity. The point addition uses field arithmetic modulo p.

Put the internal key into the hash as well as the root. This binds the offset to both inputs. A different tree typically produces a different root, tweak, and output point. The valid public relation requires knowing no secret. To prove membership later, a script-path spender reveals enough information to recreate these inputs.

Signing for the tweaked output

Alice owns a raw key d₀. First normalize it to d, matching the even internal point P. Add t in the scalar group. Because multiplying by G distributes over this addition, the preliminary scalar u yields the exact full output point Q. Now inspect Q’s Y. The signer normalizes again because the verifier lifts x(Q) to even Y, which may be −Q.

d = d₀ if y(d₀G) is even, else n − d₀
u = (d + t) mod n    reject u = 0
uG = dG + tG = P + tG = Q
q = u if y(Q) is even, else n − u
qG = lift_x(x(Q))

Only d₀, d, u, and q are private here. The original d₀ yields the internal key and its signatures bind the challenge to x(P). A key-path spend binds it to x(Q), so an original-key signature generally fails. The output parity used in a control block comes from unnormalized Q, while the signing scalar q corresponds to the even lift of x(Q).

Worked example · Check the public and private calculations agree

From scriptPubKey to bc1p

P2WPKH

00 | 14 | 20-byte HASH160(pubkey)

Version 0, Bech32. The program is a hash.

P2TR

51 | 20 | 32-byte x(Q)

Version 1, Bech32m. The program is an encoded curve coordinate.

An address is for transport. Given the version and witness program, a wallet makes the two opcodes and the program bytes above. Bech32m encodes the same 32 bytes as 52 groups of five bits, with four zero padding bits at the end. The HRP is bc on mainnet and tb on testnet, followed by separator 1. The first data word is 1, encoded as p. Six more characters encode the checksum. Bech32m uses the constant 0x2bc830a3 in place of Bech32’s 1 to address an insertion weakness in the original checksum. Version 0 still uses Bech32.

How the address checksum is computed

Expand the HRP by putting the high five-bit groups of its ASCII letters first, then a zero, then their low five-bit groups. Append the data words and six zero placeholders. Run the Bech32 polymod recurrence below, XOR the result with the Bech32m constant, and encode the resulting 30 bits as six checksum words. On decoding, polymod over the HRP expansion and all words including the checksum equals the Bech32m constant.

alphabet = qpzry9x8gf2tvdw0s3jn54khce6mua7l
chk = 1
for each expanded HRP, data, or placeholder word v:
    top = chk >> 25
    chk = ((chk & 0x1ffffff) << 5) XOR v
    for each i from 0 through 4 with bit i set in top:
        chk = chk XOR generator[i]
generator = [3b6a57b2, 26508e6d, 1ea119fa, 3d4233dd, 2a1462b3]
checksum integer = chk XOR 0x2bc830a3

The BIP86 decoding experiment breaks a published address into those fields and regroups the bits into exactly 32 program bytes.

Check your understanding

Level 1 · Why can a watch-only coordinator calculate Q?

Hint

List the inputs to TapTweak and the point addition.

Worked solution

It needs x(P), the optional root, and public group operations. The private scalar never enters that derivation.

Level 2 · In the toy curve, set d=17 and t=4. Which scalar actually signs?

Hint

2G = (6,3).

Worked solution

u=2 mod 19, Q has odd Y, so q=17 and qG=(6,14). Both points have x=6.

Level 3 · Load the official output vector and compare the 64-zero-character root. Why do the results differ?

Hint

Count the TapTweak data bytes.

Worked solution

Omission means x(P) is the entire 32-byte data. An all-zero root appends 32 bytes and changes the hash and output.
